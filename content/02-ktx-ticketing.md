## 개요, 핵심 목표, 기술 스택

### 개요

명절과 연휴에 수만 명이 동시에 같은 좌석을 예매하려 할 때 발생하는 **초과 판매(oversell), 중복 예매, 좌석 재고 깨짐**을 막고, 그 정합성과 성능을 **부하 테스트와 Before/After 수치로 증명**하는 것을 목표로 한 프로젝트다.

**N명이 한 좌석을 경합할 때 정확히 1명만 성공시키되(정합성), 그 정확성을 지키면서도 높은 처리량과 낮은 지연을 함께 보장하는(성능) 엔지니어링**이 핵심이다. 예매 동시성 보장과 성능을 부하 테스트 실측으로 검증했다.

### 핵심 목표

- **초과판매와 중복 0건**: 목표 oversell 0, 실측 **0 / 0** (3회 일관)
- **예매 응답 p95 ≤ 500ms**: 실측 **348~408ms**
- **예매 확정 처리량 ≥ 200 TPS**: 1,000 VU 실측 **833~863 TPS**

### 기술 스택

`Spring Boot 4.0` `MySQL 8` `Redis 7` `k6`

## 시스템 아키텍처

- **구성**: 시스템 구성 요소와 예매 요청 경로
- **HTML 배치**: 두 그림 좌우 2단

### 모듈 구성

| 모듈 | 역할 |
|---|---|
| **admission** | 입장 제어. 활성자 카운터로 동시 세션 상한 K, 초과분 반려. 통과 시 입장 토큰 TTL 발급 |
| **schedule** | 운행편과 잔여석 조회. Redis 단기 캐시 + single-flight로 스탬피드 방어 |
| **booking** | 예매 생성, 확정, 취소. Redis Set 원자 선점 후 MySQL 전이. `@Version` 낙관 락이 최종 방어선 |
| **reconcile** | Redis와 DB 불일치를 주기 점검, DB 기준 수렴. 감사 결과는 내부 엔드포인트로 노출 |

### 구성 요소

```
      ┌────────────────────────────────────┐
      │ Spring Boot 4.0                    │
      │ ┌─────────────┐ ┌────────────────┐ │
      │ │  admission  │ │    schedule    │ │
      │ │ 입장 제어   │ │  조회 · 캐시   │ │
      │ └─────────────┘ └────────────────┘ │
      │ ┌─────────────┐ ┌────────────────┐ │
      │ │   booking   │ │   reconcile    │ │
      │ │ 선점 · 확정 │ │ 불일치 수렴    │ │
      │ └─────────────┘ └────────────────┘ │
      └────────────────┬───────────────────┘
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
   ┌──────────────┐          ┌──────────────┐
   │   Redis 7    │          │   MySQL 8    │
   │  빠른 게이트 │          │ 정합성 원천  │
   └──────────────┘          └──────────────┘
```

- 둘이 어긋나면 **DB 기준으로 수렴**

### 예매 요청 경로

```
 K 동시 예매 세션 상한

          1,000 동시 요청
                │
    ┌───────────▼───────────┐
    │   Redis 입장 게이트   │ → HTTP 429 입장 초과
    │  INCR active:{id} ≤ K │
    └───────────┬───────────┘
                │
    ┌───────────▼───────────┐
    │    Redis 원자 선점    │ → HTTP 409 선점 실패
    │ SREM · SPOP avail:{id}│
    └───────────┬───────────┘
                │
    ┌───────────▼───────────┐
    │    MySQL  DB 전이     │ → HTTP 409 버전 충돌
    │       @Version        │
    └───────────┬───────────┘
                ▼
       확정 1건, oversell 0
```

- 선점을 꺼도 **오버셀 0** — 선점의 값은 **DB 부하 회피**

### 목표와 측정값

| 지표 | 목표 | 측정값 |
|---|---|---|
| **정합성** | 초과 판매 0 / 중복 0 | **0 / 0** (L1 단일좌석 1,000, 3회 일관) |
| 예매 응답 | p95 ≤ 500ms | **348~408ms** (L2, 3회) |
| 조회 응답 | p95 ≤ 200ms | **~26ms** (L3 핫키 · 캐시 off 8~9s) |
| 처리량 | 1,000 VU에서 ≥ 200 TPS | **833~863 TPS** (L2 · 목표의 4배) |
| 가용성 | 부하 중 5xx < 1% | **0.03~0.04%** (L2) |
| 임계점 | 무너지는 지점을 수치로 파악 | **천장 ~189 TPS → K=100 확정** (L5b) |

### Before/After 대조 실험

목표 달성만이 아니라 **각 장치를 껐을 때**를 직접 재서 그 장치의 값을 규명했다.

| 실험 | Before (끔) | After (켬) | 규명한 것 |
|---|---|---|---|
| **E1** 원자 선점 | oversell 0, reserve 중앙값 ~1.2s | oversell 0, **~0.29s** | 선점의 값은 정확성이 아니라 **DB 부하 회피** |
| **E2** 입장 제어 | p95 22s, drop 38k, VU 2,000 팽창 | **429로 85.4% 흡수**, drop 0, p95 ~28ms | 제어 부재의 비용은 5xx가 아니라 **무경계 열화** |
| **E3** 조회 캐시 | ~850 TPS, p95 8~9s | **2,497 TPS, p95 26ms** | 측정이 드러낸 지연을 캐시로 정면 해결 |

- 두 실험이 같은 결론을 가리킨다 — **정확성은 DB가 보장하고, 성능과 가용성은 앞단 게이트가 지킨다**

### 측정 신뢰성

- **부하 발생기 자신이 병목이었다** — 호스트 k6는 연결 거부가 섞여 **"진짜 1,000 동시"가 깨져 있었다**(Windows NAT 포화)
- **컨테이너 k6**로 옮겨서야 위 수치가 성립한다. 이 트러블슈팅이 곧 측정의 신뢰성을 만든 작업이다
- 시나리오는 reset → 재시드 → health → k6 → 정합성 audit을 **1회 흐름**으로 실행

## 핵심 개선과 성과

### 1. 동일 좌석 1,000명 경합 정합성 보장

- **문제**: 1,000명의 동일 좌석 동시 예매에 따른 초과 판매와 중복 예매 위험
- **해결**: Redis Set 단일 원자 선점과 DB `@Version` 최종 방어
- **성과**: 성공 1건, 초과 판매와 중복 0건(3회)

### 2. 조회 캐시 스탬피드 방어: single-flight

- **문제**: DB 재고 집계 시 p95 8~9초, TTL 만료 시 스탬피드
- **해결**: Redis TTL 1초 캐시 + single-flight
- **성과**: p95 26ms, 2,497 TPS

### 3. 비가시 입장 제어: 대기열 없이 피크 흡수

- **문제**: 입장 제어 부재 시 p95 22초, VU 2,000, 38k drop
- **해결**: Redis 활성자 카운터 `K=100`, 초과분 즉시 반려
- **성과**: 초과분 85.4% 반려, drop 0

### 4. Redis와 DB 불일치 보정: 되돌리는 쪽이 더 위험하다

- **문제**: Redis와 DB 분리 갱신으로 롤백 또는 크래시 후 불일치
- **해결**: 제거는 상시 수행하고 오버셀 위험이 있는 최근 5분 선점 복원은 보류
- **성과**: 60초 주기 DB 기준 수렴
