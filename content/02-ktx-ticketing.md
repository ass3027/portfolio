# KTX 티켓팅: 대규모 동시성 성능과 정합성 엔지니어링

- **구분**: 개인 프로젝트, 2026.06 ~ 2026.07
- **GitHub**: https://github.com/ass3027/ktx-ticketing

---

## 개요, 핵심 목표, 기술 스택

### 개요

명절과 연휴에 수만 명이 동시에 같은 좌석을 예매하려 할 때 발생하는 **초과 판매(oversell), 중복 예매, 좌석 재고 깨짐**을 막고, 그 정합성과 성능을 **부하 테스트와 Before/After 수치로 증명**하는 것을 목표로 한 프로젝트다.

**N명이 한 좌석을 경합할 때 정확히 1명만 성공시키되(정합성), 그 정확성을 지키면서도 높은 처리량과 낮은 지연을 함께 보장하는(성능) 엔지니어링**이 핵심이다. 예매 동시성 보장과 성능을 부하 테스트 실측으로 검증했다.

### 핵심 목표

- **초과판매와 중복 0건**: 목표 oversell 0, 실측 **0 / 0** (3회 일관)
- **예매 응답 p95 ≤ 500ms**: 실측 **348~408ms**
- **예매 확정 처리량 ≥ 200 TPS**: 1,000 VU 실측 **833~863 TPS**

### 기술 스택

`Spring Boot 4.0` `MySQL 8` `Redis 7` `k6`

## 시스템 아키텍처

구성과 처리 경로를 함께 본다. (HTML에서는 두 그림을 좌우 2단으로 배치)

### 구성 요소

```
      ┌────────────────────────────┐
      │     Spring Boot 4.0        │
      │                            │
      │  admission      schedule   │
      │  booking        reconcile  │
      └──────┬───────────────┬─────┘
             ▼               ▼
   ┌──────────────┐  ┌──────────────┐
   │   Redis 7    │  │   MySQL 8    │
   │  빠른 게이트 │  │ 정합성 원천  │
   │              │  │              │
   │  avail:      │  │  reservation │
   │  active:     │  │  seat_inv    │
   │  entry:      │  │  @Version    │
   │  lock:       │  │  유니크 제약 │
   └──────────────┘  └──────────────┘
```

- **Redis** 빠른 게이트. 부하를 앞단에서 흡수
- **MySQL** 정합성 원천
- 둘이 어긋나면 **DB 기준으로 수렴**

### 예매 요청 경로

```
       1,000 동시 요청
             │
    ┌────────▼─────────┐
    │   입장 게이트    │ → 429
    │   active:{id}    │
    └────────┬─────────┘
       K=100 통과
             │
    ┌────────▼─────────┐
    │    원자 선점     │ → 409
    │  SREM avail:{id} │
    └────────┬─────────┘
        승자 1명
             │
    ┌────────▼─────────┐
    │     DB 전이      │ → 409
    │    @Version      │
    └────────┬─────────┘
             ▼
    확정 1건, oversell 0
```

- 탈락 요청은 **즉시 반려**. 뒤로 흘려보내지 않음
- 앞의 두 게이트는 Redis에서 종료. **DB에 닿지 않음**
- 정확성의 최종 방어선은 `@Version` 낙관 락
- 선점을 꺼도 **오버셀 0**인 이유

### 모듈 구성

| 모듈 | 역할 |
|---|---|
| **admission** | 입장 제어. 활성자 카운터로 동시 세션 상한 K, 초과분 반려. 통과 시 입장 토큰 TTL 발급 |
| **schedule** | 운행편과 잔여석 조회. Redis 단기 캐시 + single-flight로 스탬피드 방어 |
| **booking** | 예매 생성, 확정, 취소. Redis Set 원자 선점 후 MySQL 전이. `@Version` 낙관 락이 최종 방어선 |
| **reconcile** | Redis와 DB 불일치를 주기 점검, DB 기준 수렴. 감사 결과는 내부 엔드포인트로 노출 |

### 그 밖의 흐름과 실행 환경

- **조회 경로** 위 퍼널을 타지 않음. Redis 단기 캐시로 응답, 미스일 때만 single-flight로 DB 1회
- **배경 스케줄러 2개** 만료된 좌석 보유 회수 / 어긋난 상태 수렴
- **실행** Docker Compose로 앱과 MySQL 8, Redis 7
- **부하 테스트** 별도 Compose의 k6, 지표는 Prometheus와 Grafana

## 아키텍처 결정

### Redis 동기 + 비가시 입장 제어

| 기준 | Plan A: Redis 동기 (채택) | Plan B: MQ 비동기 |
|---|---|---|
| 정합성 | 분산 락 + 낙관 락 | 파티션 직렬화 |
| 응답 UX | 단순 (요청-응답 1회) | 복잡 (추적/폴링) |
| 운영 복잡도 | 낮음 | 높음 |
| 학습/어필 | **락 설계와 경합 제어** | 스트림과 백프레셔 |

### 2단 일관성 구조

```
┌───────────────────────────────────────────────────────────┐
│ 조회 / 표시  (운행, 잔여석, 매진)                            │
│ 결과적 일관성 (staleness ≤ 2s), Redis 단기캐시               │
├───────────────────────────────────────────────────────────┤
│ 예매 확정  (락 임계영역)                                     │
│ 강한 일관성, Redis 원자선점 (SREM/SPOP) → DB 전이            │
└───────────────────────────────────────────────────────────┘
  DB = 정합성 원천, Redis = 빠른 게이트
  부하 후 Reconciliation (60s) 이 DB 기준으로 불일치 수렴
```

### 검증 목표, SLO

| 지표 / 목표 | 측정값 |
|---|---|
| 예매 응답 p95 ≤ 500ms | 348~408ms |
| 조회 p95 ≤ 200ms | 캐시 on ~26ms |
| 예매 확정 1,000 VU ≥ 200 TPS | 833~863 TPS |
| **초과판매 0 / 중복 0** | **0 / 0** (3회) |
| 5xx < 1% | 0.03~0.04% |
| 임계점 수치화 | 천장 ~189 TPS → K=100 |

### 트레이드오프

남은 좌석 수가 화면마다 달라 보이는 불일치는 버그가 아니라 조회 속도를 위해 의도적으로 감수한 트레이드오프다. 정확성이 필요한 예매 확정만 강한 일관성으로 격리하고, 그 경계를 SLO 수치(조회 staleness ≤ 2s, 초과판매 0건)로 못박았다.

## 핵심 기술적 도전

### 1. 단일 원자 선점: 1,000명 동일 좌석 경합 → 초과 판매 0건

- **문제**: 성공 1건·재고 −1 보장
- **해결**: Redis Set 단일 원자 선점 + DB `@Version` 이중 방어
- **결과**: 성공 1건, 초과 판매·중복 0건(3회)

### 2. 조회 캐시 스탬피드 방어: single-flight

- **문제**: DB 재고 집계 시 p95 8~9초, TTL 만료 시 스탬피드
- **해결**: Redis TTL 1초 캐시 + single-flight
- **결과**: p95 26ms, 2,497 TPS

### 3. 비가시 입장 제어: 대기열 없이 피크 흡수

- **문제**: 입장 제어 부재 시 p95 22초, VU 2,000, 38k drop
- **해결**: Redis 활성자 카운터 `K=100`, 초과분 즉시 반려
- **결과**: 초과분 85.4% 반려, drop 0

### 4. Redis와 DB 불일치 보정: 되돌리는 쪽이 더 위험하다

- **문제**: Redis·DB 분리 갱신으로 롤백·크래시 후 불일치
- **판단**: 제거는 언더셀, 복원은 오버셀 위험
- **해결**: 제거 상시 수행, 최근 5분 선점 복원 보류
- **결과**: 60초 주기 DB 기준 수렴

## 실험으로 증명

### 설계 결정을 수치로 증명

| 실험 | Before | After | 성과 |
|---|---|---|---|
| **동시성 제어** | 선점 OFF, reserve ~1.2s | 선점 ON, ~0.29s (~4×↓) | 정확성 동일, **DB 부하 감소** |
| **입장 제어** | 무제한, p95 22s, drop 38k | K=100, 429 85.4% 흡수, drop 0 | 무한 지연 대신 **즉시 거절** |
| **조회 캐시** | off, ~850 TPS, p95 8~9s | on, 2,497 TPS, p95 26ms | 조회 p95·DB 부하 동시 감소 |
