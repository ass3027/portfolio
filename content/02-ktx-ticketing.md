# KTX 티켓팅: 대규모 동시성 성능과 정합성 엔지니어링

- **구분**: 개인 프로젝트, 2026.06 ~ 2026.07
- **GitHub**: https://github.com/ass3027/ktx-ticketing

---

## 개요, 핵심 목표, 기술 스택

### 개요

명절과 연휴에 수만 명이 동시에 같은 좌석을 예매하려 할 때 발생하는 **초과 판매(oversell), 중복 예매, 좌석 재고 깨짐**을 막고, 그 정합성과 성능을 **부하 테스트와 Before/After 수치로 증명**하는 것을 목표로 한 프로젝트다.

CRUD 기능 수가 아니라 **N명이 한 좌석을 경합할 때 정확히 1명만 성공시키되(정합성), 그 정확성을 지키면서도 높은 처리량과 낮은 지연을 함께 보장하는(성능) 엔지니어링**이 핵심이다. 안전과 속도는 상충하기 쉬운데, 이 트레이드오프를 실측으로 풀어냈다. 7주 단계별 계획(P0~P6)으로 설계와 구현을 진행하고, 부하 시나리오 L1~L6(9종) + 필수 실험 E1~E3의 Before/After를 모두 완료했다.

### 핵심 목표

- **초과판매와 중복 0건**: 목표 oversell 0, 실측 **0 / 0** (3회 일관)
- **예매 응답 p95 ≤ 500ms**: 실측 **348~408ms**
- **예매 확정 처리량 ≥ 200 TPS**: 1,000 VU 실측 **833~863 TPS**

### 기술 스택

`Spring Boot 4.0` `Java 25` `MySQL 8` `Redis 7` `Redisson` `k6` `Testcontainers` `Gradle (Kotlin DSL)` `GitHub Actions`

## 시스템 아키텍처

```
                     ┌─────────────────────────────┐
                     │   Client, k6 부하 시나리오  │
                     └──────────────┬──────────────┘
                                    ▼
   ┌───────────────────────────────────────────────────────────────┐
   │                  Spring Boot 4.0 (Java 25)                    │
   │                                                               │
   │   admission   POST /api/entry         입장 제어 (K=100)       │
   │   schedule    GET  /api/schedules     조회 캐시, single-flight│
   │   booking     POST /api/reservations  좌석 선점, 확정         │
   │   reconcile   @Scheduled              드리프트 수렴           │
   └──────────────┬────────────────────────────────┬───────────────┘
                  ▼                                ▼
   ┌──────────────────────────────┐    ┌───────────────────────────┐
   │            Redis 7           │    │          MySQL 8          │
   │          빠른 게이트         │    │      SoT (진실의 원천)    │
   │                              │    │                           │
   │   avail:{id}    잔여 좌석 Set│    │   reservation  @Version   │
   │   active:{id}   활성자 수    │    │   seat_inventory          │
   │   entry:{token} 입장 토큰    │    │   유니크 제약             │
   │   lock:{key}    Redisson     │    │                           │
   └──────────────────────────────┘    └───────────────────────────┘
                  └── Reconciliation, DB 기준 수렴 ──┘
```

### 모듈 구성

| 모듈 | 역할 |
|---|---|
| **admission** | 입장 제어. Redis 활성자 카운터로 동시 세션을 상한 K로 제한하고, 초과분은 429/503으로 반려. 통과한 요청에는 입장 토큰을 TTL과 함께 발급 |
| **schedule** | 운행편과 잔여석 조회. Redis 공유 단기 캐시와 single-flight로 스탬피드를 막는 읽기 경로 |
| **booking** | 예매 생성, 확정, 취소. Redis Set 원자 선점으로 좌석을 잡고 MySQL로 전이, `@Version` 낙관 락이 최종 방어선 |
| **reconcile** | 스케줄러가 주기적으로 Redis와 DB 드리프트를 점검해 DB 기준으로 수렴. 감사 결과는 내부 엔드포인트로 노출 |

### 좌석 선점 경로

입장 제어를 통과한 요청만 예매 임계영역에 진입한다. 선점은 운행편별 Redis Set 한 곳에 모여 원자적으로 처리되고, 성공한 요청만 MySQL 전이로 넘어간다. 두 저장소가 어긋나면 Reconciliation이 DB 방향으로 되돌린다. 좌석 보유 만료도 별도 스케줄러가 회수한다.

### 실행 환경

Docker Compose로 애플리케이션, MySQL 8, Redis 7을 함께 띄운다. 부하 테스트는 별도 Compose로 k6를 실행하고, 지표는 Prometheus와 Grafana로 관측한다.

## 아키텍처 결정

### Redis 동기 + 비가시 입장 제어

| 기준 | Plan A: Redis 동기 (채택) | Plan B: MQ 비동기 |
|---|---|---|
| 정합성 | 분산 락 + 낙관 락 | 파티션 직렬화 |
| 응답 UX | 단순 (요청-응답 1회) | 복잡 (추적/폴링) |
| 운영 복잡도 | 낮음 | 높음 |
| 학습/어필 | **락 설계와 경합 제어** | 스트림과 백프레셔 |

### 2단 일관성 구조

```
┌───────────────────────────────────────────────────────────┐
│ 조회 / 표시  (운행, 잔여석, 매진)                            │
│ 결과적 일관성 (staleness ≤ 2s), Redis 단기캐시               │
├───────────────────────────────────────────────────────────┤
│ 예매 확정  (락 임계영역)                                     │
│ 강한 일관성, Redis 원자선점 (SREM/SPOP) → DB 전이            │
└───────────────────────────────────────────────────────────┘
  DB = SoT (진실의 원천), Redis = 빠른 게이트
  부하 후 Reconciliation (60s) 이 DB로 드리프트 수렴
```

### 검증 목표, SLO

| # | 지표 / 목표 | 측정값 (P4) |
|---|---|---|
| S1 | 예매 응답 p95 ≤ 500ms | 348~408ms |
| S2 | 조회 p95 ≤ 200ms | 캐시 on ~26ms |
| S3 | 예매 확정 1,000 VU ≥ 200 TPS | 833~863 TPS |
| **S4** | **초과판매 0 / 중복 0** | **0 / 0** (3회) |
| S5 | 5xx < 1% | 0.03~0.04% |
| S6 | 임계점 수치화 | 천장 ~189 TPS → K=100 |

### 트레이드오프

남은 좌석 수가 화면마다 달라 보이는 불일치는 버그가 아니라 조회 속도를 위해 의도적으로 감수한 트레이드오프다. 정확성이 필요한 예매 확정만 강한 일관성으로 격리하고, 그 경계를 SLO 수치(S2 staleness ≤ 2s, S4 oversell 0)로 못박았다.

## 핵심 기술적 도전

### 1. 단일 원자 선점: 1,000명 같은 좌석 경쟁 → 초과 판매 0건

- **문제**: N명이 같은 좌석을 동시 시도해도 성공은 단 1명, 재고는 정확히 −1이어야 함. 락을 흩뿌리면 경합 지점 증가로 정합성 붕괴.
- **성과 (L1 실측)**: 선점을 단일 원자 지점(Redis Set `SREM`/`SPOP`)에 모으고 DB `@Version` 낙관락으로 이중 방어. 1,000명 경쟁 → 성공 정확히 **1건**, **초과판매와 중복 0**(3회 일관).

### 2. 조회 캐시 스탬피드 방어: single-flight (E3)

- **문제**: 조회는 모든 사용자의 진입점이라 읽기가 압도적. 매 요청이 DB에서 재고를 집계하면 조회 p95 8~9초로 붕괴, TTL 만료 순간 스탬피드 위험.
- **성과**: Redis 공유 단기 캐시(TTL 1s) + single-flight(winner 1개만 재계산)로 방어. 핫키 조회 **p95 8~9s → 26ms**, 처리량 **~850 → 2,497 TPS**(저히트율 한계도 함께 규명).

### 3. 비가시 입장 제어: 대기열 없이 피크 흡수 (E2)

- **문제**: 대기 순번 비노출 상태로 피크를 견뎌야 함. 입장 제어 부재 시 무경계 열화(p95 22s, VU 2,000 팽창, 38k drop)로 조용히 붕괴.
- **성과**: Redis 활성자 카운터로 동시 세션을 상한 `K=100`으로 제한, 초과분은 `429/503+Retry-After`로 흡수. **초과분 85.4%를 429로 흡수, dropped 0**.

### 4. Redis↔DB 드리프트 수렴: DB를 SoT로

- **문제**: 빠른 게이트(Redis)는 언제든 틀릴 수 있음. 부하 중 Redis `avail` Set ↔ DB 상태 드리프트 발생, 방치 시 오버셀로 번짐.
- **성과**: `ReconciliationService`(60s)가 드리프트를 **DB(SoT)로 수렴**(비대칭 방향, grace 5분). Redis는 게이트, DB는 SoT라는 계약을 닫아 **오버셀 원천 차단**.

## 실험으로 증명 & 배운 점

### 설계 결정을 수치로 증명

| 실험 | Before | After | 보여준 것 |
|---|---|---|---|
| **E1** 동시성 제어 | 선점 OFF, reserve ~1.2s | 선점 ON, ~0.29s (~4×↓) | 선점의 값 = **DB 부하 회피** (정확성은 양쪽 0) |
| **E2** 입장 제어 | 무제한, p95 22s, drop 38k | K=100, 429 85.4% 흡수, drop 0 | 무경계 열화 → 빠른 반려 |
| **E3** 조회 캐시 | off, ~850 TPS, p95 8~9s | on, 2,497 TPS, p95 26ms | 조회 p95와 DB 부하 대폭 감소 |

### E1의 정직한 결론

선점을 꺼도 `@Version` 낙관 락과 DB 유니크가 오버셀을 막아 정확성은 양쪽 0이다. 선점의 값은 정확성의 필요조건이 아니라 DB 부하 회피다. 정확성은 DB가 보장하고 성능과 가용성은 앞단 게이트가 지킨다는 2-tier 서사를 세 실험이 실측으로 뒷받침한다.

### 배운 점

| 항목 | 내용 |
|---|---|
| 동시성과 정합성 | Redis 원자 선점 + DB 낙관 락 이중 방어로 1,000 경합에서 oversell 0을 설계하고 증명. |
| 2-tier 일관성 | 조회는 약한 일관성, 예매는 강한 일관성으로 명시 분리, 경계를 SLO로 측정 가능하게 함. |
| 부하 테스트 | k6로 L1~L6 + E1~E3 Before/After를 설계, SLO 충족 여부를 수치로 판정. |
| 측정 후 최적화 | 추측성 최적화를 배제하고 병목으로 측정될 때만 착수하도록 트리거 조건을 명문화. |
| 근본 원인 규명 | 1,000 동시 연결 거부의 진짜 원인이 앱이 아닌 Docker NAT 포화임을 격리 실험으로 규명. |
| AI 통제 워크플로우 | 계획, 테스트 유효성, 커밋 승인 3개 사람 게이트로 AI에 끌려가지 않는 협업 규율 확립. |
