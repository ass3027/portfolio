# AI 워크플로우

- **구분**: 개인 프로젝트, 2026

---

## 프로젝트 요약

### 개요

AI 에이전트를 코드 생성 도구가 아닌 책임 경계, 승인 게이트, 검증 규칙을 갖춘 협업 시스템으로 설계하고 실제 작업에 적용했다. 코드 리뷰 결과를 후속 작업으로 연결하는 자동화와, 모든 개발 작업에 적용하는 AI 협업 규율을 각각 구축했다.

### 핵심 목표

- **개선 루프 구축**: 코드 리뷰, 이슈 발행, 팀 알림, 후속 작업 착수 연결
- **승인과 책임 경계**: 외부 상태 변경과 되돌리기 어려운 작업의 사람 승인 적용
- **세션 간 상태 관리**: 작업 목록, 테스트, Git 이력 기반 실행 기준 유지

### 기술

`AI Agent` `GitLab REST API / WebHook` `KakaoWork` `Git`

## 사례 1. 사내 프로젝트 개선 파이프라인

### 문제와 목표

코드 리뷰 결과가 보고로 끝나면 이슈 발행, 팀 공유, 실제 수정 작업까지 이어지지 않는다. 분석 결과를 승인 가능한 이슈와 후속 작업으로 전환하는 개선 루프를 목표로 했다.

### 워크플로우

```
프로젝트
   │
   ▼
문제점 분석
   │
   ├── 승인 ──► 이슈 발행 ──► 카카오워크 알림
   │                              │
   │                              ▼
   │                         이슈 작업 목록화
   │                              │
   └──────────────── 승인 ◄───────┤
                                  ▼
                             작업 착수
                                  │
                                  └──── 개선 결과 환류 ────► 문제점 분석
```

- **분석**: `project-review`를 활용한 품질, 보안, 버그, 빌드 4개 영역 점검과 파일, 라인 근거 수집
- **이슈 발행**: 이슈 초안 요약과 제시, 승인 항목만 GitLab REST API 발행
- **알림과 작업화**: GitLab WebHook과 카카오워크 연동, `review-import-issues` 기반 심각도 순 작업 목록화
- **작업 착수**: 승인 후 우선순위 기반 구현과 검증, 결과의 다음 분석 단계 환류

### 승인 게이트

| 단계 | 자동화 역할 | 사람의 역할 |
|---|---|---|
| 분석 | 코드베이스 점검, 근거 수집, 이슈 초안 작성 | 결과와 우선순위 검토 |
| 이슈 발행 | 승인 항목의 GitLab REST API 발행 | 발행 대상 승인 |
| 작업 착수 | 계획, 구현, 테스트 제안과 실행 | 작업 범위와 계획 승인 |

분석과 반복 작업은 자동화하고, 외부 상태를 바꾸는 이슈 발행과 작업 착수는 사람이 승인한다. 자동화 속도와 변경 통제력을 함께 확보하기 위한 경계다.

### 성과

- **개선 루프**: 코드 리뷰 결과를 승인 이슈, 팀 알림, 후속 작업, 재분석으로 연결
- **개발 현황 공유**: 현재 상태 리뷰와 신규 기능 개발 진행을 카카오워크 채널로 빠르게 공유
- **실행 근거 보존**: 파일과 라인 근거 기반 지적, 승인된 변경만 실행하는 흐름 정착

## 사례 2. 공통 인간·AI 협업 워크플로우

### 문제와 목표

대화형 작업 목록만으로는 세션이 바뀐 뒤 작업 선정 근거, 진행 상태, 검증 결과를 복원하기 어렵다. 모든 개발 작업에 계획, 승인, 검증 기준을 적용하고 저장소 안의 문서와 Git 이력으로 실행 상태를 유지하는 것을 목표로 했다.

### 워크플로우

```
설계·계획 문서
      │ 작업 추출
      ▼
Task_Checklist: 단일 기준
      │
      ▼
다음 작업 선정 → 계획 → 승인 → 구현과 테스트 → 테스트 검토 → 커밋
                                      │                         │
                                      └────── Phase 결과 문서 ◄─┘
                                                        │
                                                        └── 체크리스트 갱신
```

### 운영 규율

| 규율 | 내용 |
|---|---|
| **작업 목록 우선 생성** | 설계 문서의 `Task_Checklist` 전개, 실행 상태의 단일 기준 적용 |
| **계획과 승인 우선** | 계획 승인 전 구현 금지, 커밋 메시지 사전 승인 적용 |
| **진행 상태의 단일 기준화** | 휘발성 TaskList 대신 Git 이력과 작업 목록으로 상태 관리 |
| **테스트 범위 명확화** | 언어와 프레임워크 자체 동작 제외, 핵심 비즈니스 로직 검증 |
| **소단위 커밋** | 엔티티, 설정, 테스트, 문서 등 관심사별 커밋 분리 |
| **Phase 단위 검토** | 결과 문서 기반 목표 충족 여부 검토, 체크리스트 마감 |

### 성과

- **세션 간 맥락 복원**: `Task_Checklist`, Git 이력, Phase 결과 문서 기반 작업 근거와 다음 작업 확인
- **일관된 실행 기준**: 계획, 승인, 테스트, 커밋의 공통 규율 적용
- **검증 범위 명확화**: 핵심 비즈니스 로직 중심 테스트와 관심사별 변경 단위 관리
