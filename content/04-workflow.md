# AI 워크플로우

- **구분**: 개인 프로젝트, 2026

---

## 사례 1. 사내 프로젝트 개선 루프

### 기술 스택

`AI Agent` `GitLab REST API / WebHook` `KakaoWork` `Git`

### 개요와 목표

코드 리뷰와 작업 배분을 자동화해 **팀 생산성을 높이는 것**이 목표다. 분석은 AI에 맡기되, **각 단계에 승인을 두어** 사람이 확인한 것만 다음으로 넘어간다.

LLM을 **GitLab에 연결하고 GitLab과 카카오워크를 연동**해, 분석 결과가 이슈 발행과 팀 공유, 작업 착수까지 **사내 업무 프로세스 위에서 이어지게** 만들었다.

### 워크플로우

```
프로젝트
   │
   ▼
코드 리뷰
   │
   ├── 승인 ──► 이슈 발행 ──► 카카오워크 알림
   │                              │
   │                              ▼
   │                         이슈 가져오기
   │                              │
   └──────────────── 승인 ◄───────┤
                                  ▼
                             작업 착수
                                  │
                                  └──── 개선 결과 환류 ────► 코드 리뷰
```

- **코드 리뷰**: `project-review`를 활용한 품질, 보안, 버그, 빌드 4개 영역 점검과 파일, 라인 근거 수집
- **이슈 발행**: 이슈 초안 요약과 제시, 승인 항목만 GitLab REST API 발행
- **팀 알림**: GitLab WebHook과 카카오워크 연동
- **이슈 가져오기**: 발행된 이슈를 `review-import-issues`로 회수, 심각도 순 작업 목록 구성
- **구현과 검증**: 작업 범위와 계획 승인 후 구현과 검증, 결과의 다음 리뷰 환류

### 검토/승인 대상

| 단계 | 자동화 역할 | 사람의 역할 |
|---|---|---|
| 코드 리뷰 | 코드베이스 점검, 근거 수집, 이슈 초안 작성 | 결과와 우선순위 검토 |
| 이슈 발행 | 승인 항목의 GitLab REST API 발행 | 발행 대상 승인 |
| 작업 착수 | 계획과 구현 제안, 승인 후 실행 | 작업 범위와 계획 승인 |

분석과 반복 작업은 자동화하고, 외부 상태를 바꾸는 이슈 발행과 작업 착수는 사람이 승인한다. 자동화 속도와 변경 통제력을 함께 확보하기 위한 경계다.

### 성과

- **개선 루프**: 사람이 옮겨 적던 이슈 등록과 작업 배분이 승인만으로 처리
- **개발 현황 공유**: 따로 묻지 않아도 리뷰 결과와 개발 진행이 카카오워크 채널로 도착
- **실행 근거 보존**: 구두 지적 대신 파일과 라인 근거, 승인된 변경만 실행하는 흐름 정착

## 사례 2. 공통 인간·AI 협업 워크플로우

### 문제와 목표

대화형 작업 목록만으로는 **세션이 바뀐 뒤** 작업 선정 근거, 진행 상태, 검증 결과를 **복원하기 어렵다**. 모든 개발 작업에 계획, 승인, 검증 기준을 적용하고 **저장소 안의 문서와 Git 이력으로 실행 상태를 유지**하는 것을 목표로 했다.

### 워크플로우

```
설계·계획 문서
      │ 작업 추출
      ▼
Task_Checklist: 단일 기준
      │
      ▼
다음 작업 선정 → 계획 → 승인 → 구현과 테스트 → 테스트 검토 → 커밋
                                      │                         │
                                      └────── Phase 결과 문서 ◄─┘
                                                        │
                                                        └── 체크리스트 갱신
```

### 운영 규율

| 규율 | 내용 |
|---|---|
| **작업 목록 우선 생성** | 설계 문서의 `Task_Checklist` 전개, 실행 상태의 단일 기준 적용 |
| **계획과 승인 우선** | 계획 승인 전 구현 금지, 커밋 메시지 사전 승인 적용 |
| **진행 상태의 단일 기준화** | 휘발성 TaskList 대신 Git 이력과 작업 목록으로 상태 관리 |
| **테스트 범위 명확화** | 언어와 프레임워크 자체 동작 제외, 핵심 비즈니스 로직 검증 |
| **소단위 커밋** | 엔티티, 설정, 테스트, 문서 등 관심사별 커밋 분리 |
| **Phase 단위 검토** | 결과 문서 기반 목표 충족 여부 검토, 체크리스트 마감 |

대화는 세션과 함께 사라지지만 저장소와 Git 이력은 남는다. 상태를 사람의 기억이나 대화창이 아닌 저장소에 두기 위한 규율이다.

### 성과

- **세션 간 맥락 복원**: 대화가 끊기면 사라지던 선정 근거와 진행 상태를 저장소에서 확인
- **일관된 실행 기준**: 작업마다 달라지던 진행 방식이 계획, 승인, 검증의 같은 순서로 고정
- **변경 단위 관리**: 뭉쳐 올리던 변경을 관심사별 커밋으로 분리, 이력 추적 가능
