# AI 활용: 코드 리뷰 자동화와 공통 개발 흐름 설계

- 적용 대상: 사내 프로젝트 리뷰와 Tag2Now 백엔드 개발 및 검증
- 기술 스택: `AI Agent` `GitLab REST API` `WebHook` `KakaoWork` `basedpyright` `Import Linter` `pytest`

## 핵심 개선과 성과: 사내 코드 리뷰와 이슈 발행

### 덱 표시

- AI 에이전트가 `project-review` 스킬로 저장소 분석부터 승인된 GitLab 이슈 발행까지 실행합니다.

| 위치 | 표시 문구 |
|---|---|
| 왼쪽 상위 스킬 | `project-review`로 리뷰와 이슈 발행 조율 |
| 왼쪽 하위 스킬 | `analyze-metadata`로 기술 스택, 빌드 명령, 이슈 트래커 확인 |
| 왼쪽 하위 스킬 | `organize-tasks`로 발견 사항 분류와 이슈 초안 작성 |
| 왼쪽 하위 스킬 | `publish-issues`로 GitLab REST API로 승인된 이슈 발행 |
| 왼쪽 참조 문서 | `checklist.md`에서 공통 기준과 기술 스택별 검수 항목 확인 |
| 오른쪽 실행 흐름 | 저장소 분석 → 에이전트 코드 리뷰 → 이슈 초안 → 사람의 발행 승인 → GitLab 등록 |
| 리뷰 범위와 근거 | 품질, 보안, 버그, 빌드 점검 / 파일과 라인 근거 기록 |
| 초안 산출물 | 우선순위와 근거를 담은 초안 |
| 발행 승인 | 사람이 발행할 이슈 선택 |
| 발행 이후 | KakaoWork 자동 알림 |
| 오른쪽 실행 흐름 내 후속 개발 | GitLab 등록 아래 가로 배치. 이슈 회수 → 구현 계획 → 사람의 착수 승인 → 구현과 검증 |

### 문제

- 리뷰 결과의 수동 이슈 등록과 팀 공유
- 분석 결과와 후속 개발 작업의 분리
- 세션 종료에 따른 작업 근거와 진행 상태 유실

### 해결

| 단계 | AI와 연동 도구 | 사람의 판단 |
|---|---|---|
| 코드 리뷰 | 공통 기준과 스택별 체크리스트 적용, 품질, 보안, 버그, 빌드 점검, 파일과 줄 번호를 포함한 근거 기록 | 지적의 타당성과 우선순위 |
| 이슈 초안 | 발견 사항 분류와 이슈 본문 작성 | 수정 대상과 제외 항목 |
| 이슈 발행 | GitLab REST API 호출 | 발행 대상 승인 |
| 팀 공유 | GitLab WebHook과 KakaoWork 연동 | 공유된 결과 확인 |
| 작업 착수 | 이슈 회수와 구현 계획 작성 | 범위와 계획 승인 |
| 작업 종료 | 구현, 검증 결과와 작업 목록 갱신 | 목표 충족 여부 검토 |

### 성과

- 리뷰 근거에서 이슈와 후속 작업으로 이어지는 흐름 구성
- 이슈 등록과 팀 공유의 반복 작업 자동화
- 작업 목록과 Git 이력을 통한 세션 간 상태 확인

### 설계 판단

분석과 초안 작성은 자동화하고, 이슈 발행과 작업 착수에는 사람의 승인을 두었습니다. 승인 경계는 제안이 외부 상태와 실제 코드 변경으로 이어지는 시점에 배치했습니다.

### 실행 상태의 기준

- 작업 범위: 승인된 계획
- 진행 상태: 저장소의 작업 목록
- 완료 근거: 검증 결과와 변경 이력

## 핵심 개선과 성과: AI 에이전트 기반 개발 흐름

### 덱 표시

구현 전에 계획을 검토하고 커밋 전 필수 검증이 빠지지 않도록, 사용자 공통 지침과 스킬에 작업 절차를 정했습니다.

| 담당 | 단계 | 확인할 내용 |
|---|---|---|
| 나 | 변경 요청 | 변경 목표와 제약 전달 |
| AI 에이전트 | 구현 전 탐색 | 재사용할 코드와 테스트 |
| AI 에이전트 | 계획 제안 | 재사용 범위, 새 구현 근거 제시 |
| 나 | 구현 착수 승인 | 수정 범위와 재사용 근거 |
| AI 에이전트 | 구현 | 계층 경계 준수, 공개 동작 테스트 보강 |
| AI 에이전트 | 구현 후 테스트 | 변경 범위 테스트와 결과 보고 |
| AI 에이전트 | 동작 테스트 | 스킬 `test` 배지 |
| AI 에이전트 | 구조 및 타입 검사 | 스킬 `inspect` 배지 |
| AI 에이전트 | 커밋 계획 제안 | 커밋별 파일과 메시지 |
| 나 | 커밋 계획 승인 | 파일과 메시지 검토 |
| AI 에이전트 | `commit` | 승인 파일만 커밋, SHA와 결과 보고 |

- 커밋 흐름 제목 아래 문구: 내 커밋 요청 후 필수 검증 자동 실행 → 통과 시 커밋 계획 제안
- `공통 지침` 배지 위치는 구현 착수 승인 카드 하단

#### 적용 방식

| 구성 | 역할 |
|---|---|
| 사용자 공통 지침 | 기존 코드와 테스트의 재사용 범위를 계획에 명시하고, 승인 후 구현 |
| 에이전트 스킬 | `test` 단위 및 통합 테스트<br>`inspect` 린트, 포맷, 의존성 및 타입 검사<br>`git-commit-helper` 커밋 계획 제안과 승인 후 커밋 |

#### 적용 사례

| 실행 시점 | 에이전트 실행 지시 |
|---|---|
| 구현 및 커밋 전 | 사용자 수준의 `AGENTS.md`와 `CLAUDE.md`에 구현 전 계획 승인과 명시적 커밋 요청 규칙 명시 |
| 구현 착수 전 | 포트폴리오 저장소의 `AGENTS.md`에 구현 계획 제시와 승인 절차 명시 |
| 커밋 요청 후 검증 | Tag2Now 백엔드의 `CLAUDE.md`에 따라 `test` → `inspect` 순서로 실행<br>`pytest` 단위 및 통합 테스트<br>Ruff 린트 및 포맷 검사<br>Import Linter 의존성 검사<br>`basedpyright` 타입 검사 |
| 커밋 요청 후 계획 및 실행 | 공통 `git-commit-helper` 스킬로 커밋 계획 제시, 사용자 승인 후 커밋과 결과 보고 |

#### 공통 작업 규칙

| 단계 | 공통 작업 규칙 |
|---|---|
| 작업 계획 | 요청 진입점부터 처리 로직과 관련 테스트까지 추적<br>변경 파일, 재사용할 코드와 픽스처, 확인할 동작 기록<br>새 구현이 필요한 경우 기존 구조로 처리하기 어려운 이유 명시 |
| 코드와 테스트 작성 | 계획에서 확인한 계층과 진입점을 따라 구현<br>변경 동작별 입력과 기대 결과 정의<br>공개 API 또는 서비스의 결과 검증<br>기존 테스트 보강, 누락된 동작에만 케이스 추가 |
| 동작 테스트 (`test`) | 공개 API 또는 서비스의 기대 동작을 확인하는 테스트 실행<br>도구 예시 `pytest`, `JUnit`, `Playwright` |
| 구조 및 타입 검사 (`inspect`) | 프로젝트의 린트, 포맷, 의존성, 계층, 타입 규칙 검사<br>도구 예시 `Import Linter`, `ArchUnit`, `basedpyright` |
| 커밋 | 검증 실패 시 결과 보고 및 커밋 보류<br>모든 검증 통과 후 관련 변경을 커밋 단위로 묶어 계획 제시<br>사용자가 승인한 파일과 메시지로 커밋<br>커밋 SHA, 메시지, 검증 결과, 작업 트리 상태 보고 |

### 문제

- 기능 단위 구현에서 기존 코드와 테스트의 재사용 누락
- 프로젝트의 계층 규칙을 벗어나는 의존성 추가
- 기존 테스트와 검증 범위 중복

### 해결

- 작업 계획에 수정 대상과 재사용 판단의 근거 기록
- 변경된 동작을 공개 인터페이스의 입력과 기대 결과에 연결
- `basedpyright`로 애플리케이션 코드와 테스트의 타입 검사
- Import Linter로 모듈 의존성 규칙 검사
- `pytest`로 단위 및 통합 테스트 실행
- `git-commit-helper`로 커밋 단위와 메시지 제안, 사용자 승인 후 커밋 및 결과 보고

### 성과

- 적용: Tag2Now 백엔드의 `CLAUDE.md`에서 커밋 계획 제안 전 `test`와 `inspect` 실행 지시
- 적용: 공통 `git-commit-helper`에 커밋 계획 제시, 사용자 승인, 결과 보고 절차 정의
- 적용: CI에 타입 검사, 의존성 검사, 테스트 실행 구성

### 후속 계획

- 구현 전 탐색과 테스트 작성 기준의 공통 스킬 적용, 저장소 간 재사용
- 코드 변경 작업 시작 시 공통 스킬 실행 지침 명시
- 에이전트 훅으로 정해진 시점에 검증 명령 실행, 검사 누락 방지
