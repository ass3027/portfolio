# KTX: 동시성 제어 장치의 효과를 비교 실험으로 검증

- 구분: 개인 프로젝트, 2026.06 ~ 2026.07
- GitHub: https://github.com/ass3027/ktx-ticketing
- 기술 스택: `Spring Boot` `MySQL` `Redis` `k6`

## 핵심 개선과 성과: 정확성과 부하 제어의 책임 분리

### 덱 표시

- MySQL이 초과 판매를 막고, Redis가 경합 요청의 DB 접근을 줄이도록 구성했습니다.
- 검증 조건 · 단일 좌석에 1,000명 동시 요청 · 로컬 Docker Compose · 3회 반복

| 단계 | 표시 문구 |
|---|---|
| 1 | Redis 입장 제어 · 초과 요청 HTTP 429 |
| 2 | Redis 원자 선점 · 동일 좌석 경쟁 제어 |
| 3 | MySQL 최종 검증 · 낙관적 잠금 |
| 결과 | 예매 성공 1건 · 초과 판매 0건 |

### 문제

- 동일 좌석의 동시 예매에 따른 초과 판매와 중복 위험
- 경합 요청의 DB 집중
- 피크 요청 증가 시 응답 지연과 부하 확산

### 해결

| 구성 | 담당 책임 |
|---|---|
| Redis 입장 제어 | 활성 예매 세션 상한 적용 |
| Redis 원자 선점 | 재고 경합 요청의 DB 접근 축소 |
| MySQL `@Version` | 예약 상태 전이의 최종 충돌 방어 |
| Redis 조회 캐시와 single-flight | 집계 조회의 반복 실행 억제 |
| 주기적 보정 | DB 기준의 Redis 상태 수렴 |

### 성과

- 동일 좌석 1,000명 경합 시 성공 1건
- 초과 판매와 중복 예매 0건
- L1 시나리오의 3회 반복 결과 일치

### 검증으로 구분한 역할

원자 선점을 끈 경우에도 초과 판매는 발생하지 않았습니다. 정합성의 최종 방어는 DB가 담당하며, Redis 선점의 효과는 충돌 요청의 DB 부하를 줄이는 데 있었습니다.

### 운영 판단

- 불일치 보정: DB를 기준으로 수렴
- 복원 정책: 최근 선점의 즉시 복원 보류
- 관측 경로: Prometheus의 앱 메트릭 조회와 Grafana의 PromQL 조회

## 핵심 개선과 성과: OFF/ON 비교와 측정 조건 검증

### 덱 표시

- 기능별 OFF/ON 비교로 예약 경합, 조회 지연, 과부하 대응의 변화를 확인했습니다.
- 측정 환경 · 로컬 Windows Docker Compose · 입장 제어 반려는 HTTP 429

| 비교 | 측정 범위 | OFF 주요값 | OFF 보조값 | ON 주요값 | ON 보조값 |
|---|---|---|---|---|---|
| 원자 선점 | 예매 reserve 중앙값 | 약 1.2초 | 초과 판매 0건 | 약 0.29초 | 초과 판매 0건 |
| 조회 캐시 | L3 핫키 조회 p95 | 약 8~9초 | 약 850 TPS | 약 26ms | 2,497 TPS |
| 입장 제어 | 과부하 시 drop 건수 | 약 38,000건 | 전체 p95 약 22초 | 0건 | 초과 요청 85.4% 반려 |

### 문제

- 장치의 적용 여부만으로 효과 판별 불가
- 호스트 k6 실행 시 Windows NAT 포화
- 동시 연결 부족에 따른 부하 조건 왜곡

### 해결

- k6의 앱과 동일한 Docker 네트워크 배치
- 초기화, 재시드, 상태 확인, 부하, 정합성 검사의 연속 실행
- 원자 선점, 입장 제어, 조회 캐시의 OFF/ON 비교
- 시나리오별 정합성, 지연과 처리량 구분

### 성과

| 비교 대상 | OFF | ON | 확인한 효과 |
|---|---|---|---|
| 원자 선점 | 초과 판매 0, reserve 중앙값 약 1.2초 | 초과 판매 0, 약 0.29초 | DB 경합 비용 축소 |
| 조회 캐시 | p95 약 8~9초, 약 850 TPS | p95 약 26ms, 2,497 TPS | 반복 집계 비용 축소 |
| 입장 제어 | p95 약 22초, drop 약 38,000건 | 초과 요청 85.4% 반려, drop 0 | 과부하 시 초과 요청 제한 |

### 시나리오별 측정 범위

- L1: 단일 좌석의 경합과 초과 판매 검사
- L2: 1,000 VU 예매 부하, p95 348~408ms, 833~863 TPS
- L3: 핫키 조회의 캐시 OFF/ON 비교
- 입장 제어의 반려 응답: HTTP 429
- 측정 환경: 로컬 Windows의 Docker Compose

### 실험 해석

초과 요청을 반려하는 실험의 전체 응답 지연과 승인된 예매의 처리 성능은 구분해야 합니다. 정합성, 예매 처리 성능, 조회 성능과 과부하 대응을 각각의 시나리오에서 판단합니다.
