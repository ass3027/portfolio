## Tag2Now: 철권 태그2 실시간 대시보드

원문: 4~7쪽.

- 기간 및 역할: 2026.03~2026.05, 개인 프로젝트, 1인 풀스택.
- 기술: FastAPI, Redis, PostgreSQL, AWS, GitHub Actions.
- GitHub: [Tag2Now 저장소](https://github.com/orgs/tag2now/repositories).
- 서비스: [match.tag2now.click](https://match.tag2now.click/).

### 개요와 목표

원문: 4쪽.

- 대상: RPCS3 에뮬레이터로 TTT2를 즐기는 커뮤니티.
- 문제: 활성 사용자 수, 매칭 상대, 랭킹 정보 확인 도구 부재.
- 제약: RPCN의 게임별 호출 방식 미문서화, 공식 SDK 부재.
- 접근: Rust RPCN 서버 직접 실행과 분석, 바이너리 프로토콜 역공학, Python 클라이언트 구현과 단위 및 통합 테스트.
- 목표: 프로토콜 구현, 조회 API가 제공하지 않는 매칭 상태 시각화, 개인 부담 가능한 비용의 서비스 운영.

### 시스템 아키텍처

원문: 5쪽.

```text
RPCN Server (PSN)
  TCP/TLS, Binary + Protobuf
        |
FastAPI Application
  RpcnClient
  Matching / History / Community
        |
  Redis 캐시 / PostgreSQL 및 DynamoDB 저장소 표기
```

| 모듈 | 역할 |
| --- | --- |
| RpcnClient | 역공학한 바이너리 프로토콜, TCP/TLS 세션, 명령 7종 |
| Matching | 방과 리더보드 실시간 수집, Redis 캐시, 매칭 탐지 |
| History | 스냅샷의 PostgreSQL 저장, 시간별 및 일별 통계 집계 |
| Community | 게시판과 댓글 CRUD |

## KTX 티켓팅

원문: 8~11쪽.

- 기간: 2026.06~2026.07.
- 구분: 개인 프로젝트, 부하 테스트 검증.
- 기술: Spring Boot, MySQL, Redis, k6.
- GitHub: [ktx-ticketing](https://github.com/ass3027/ktx-ticketing).

### 개요와 목표

원문: 8쪽.

- 문제 상황: 같은 좌석에 요청 집중, 초과 판매, 중복 예매, 재고 불일치.
- 정합성 목표: 한 좌석을 N명이 경합해도 정확히 1명 확정.
- 성능 목표: 정합성을 유지하면서 처리량과 응답 지연 개선.
- 검증 방식: SLO 기준 설정, k6 실측, 장치별 OFF/ON 비교.
- 목표 시나리오와 실측 구분: 수만 명의 예매 상황을 문제 배경으로 제시. 수만 명 실측 결과라는 의미는 아님.

### 시스템 구성과 예매 요청 경로

원문: 9쪽.

- 실행 경계: Docker Compose 단일 네트워크.
- 요청: k6 1,000 VU -> HTTP API -> Spring Boot.
- 모듈: admission 입장 제어, schedule 조회와 캐시, booking 예약 트랜잭션, reconcile 불일치 보정.
- 저장소: Redis 대기열 상태 및 조회 캐시, MySQL 예약 원장과 정합성.
- 관측: Prometheus의 앱 메트릭 scrape, Grafana의 PromQL query.

```text
예매 요청
  -> Redis 활성자 입장 게이트: INCR active:{id} <= K
       초과: HTTP 429
  -> Redis 원자 선점: SREM / SPOP avail:{id}
       실패: HTTP 409
  -> MySQL 상태 전이: @Version
       버전 충돌: HTTP 409
  -> 단일 좌석 경합의 확정 1건, oversell 0
```

정합성 최종 방어는 DB다. 원자 선점을 꺼도 오버셀 0이며, 선점의 가치는 DB 부하 회피라는 설명이다. 입장 제어와 좌석 선점은 서로 다른 단계다.

### 장치별 OFF/ON 비교

원문: 10쪽.

| 장치 | OFF | ON | 원문의 판단 |
| --- | --- | --- | --- |
| 원자 선점 | oversell 0, reserve 중앙값 약 1.2초 | oversell 0, 중앙값 약 0.29초 | 선점의 가치: DB 부하 회피 |
| 입장 제어 | p95 22초, drop 38k, VU 2,000 팽창 | HTTP 429로 85.4% 흡수, drop 0 | 제어 부재의 비용: 무경계 열화 |
| 조회 캐시 | 약 850 TPS, p95 8~9초 | 2,497 TPS, p95 26ms | 측정으로 확인한 조회 지연 해소 |

- 부하 생성 조건: k6 컨테이너 실행.
- 초기 문제: 호스트 실행 시 Windows NAT 포화와 연결 거부.
- 측정 영향: 실제 1,000 동시 접속 미달.
- 제한: L1, L2, L3, L5b 및 장치별 비교의 동일 조건 여부와 상세 executor는 PDF만으로 확정 불가.
- 해석: 개인 부하 테스트 수치. 실서비스 사용자 트래픽 운영 성과로 표현하지 않음.
- 해석: 요청 처리량과 실제 예매 확정 건수 구분 필요. TPS의 집계 정의는 실험 자료 확인.
- 해석: 낮은 5xx 비율만으로 업무 성공률 확정 불가. 409와 429의 별도 의미 확인.

### 핵심 개선과 성과

원문: 11쪽.

| 사례 | 문제 | 해결 | 성과 |
| --- | --- | --- | --- |
| 동일 좌석 정합성 | 1,000명 경합의 초과 판매와 중복 위험 | Redis Set 원자 선점, DB @Version 최종 방어 | 성공 1건, 초과 판매 및 중복 0건, 3회 |
| 조회 캐시 스탬피드 | DB 재고 집계 p95 8~9초, TTL 만료 시 요청 집중 | Redis TTL 1초와 single-flight | p95 26ms, 2,497 TPS |
| 비가시 입장 제어 | 미적용 시 p95 22초, VU 2,000, 38k drop | 활성자 카운터 K=100, 초과 즉시 반려 | 초과분 85.4% 반려, drop 0 |
| Redis와 DB 보정 | 분리 갱신, 롤백 및 크래시 후 불일치 | 제거 상시 수행, 최근 5분 선점 복원 보류 | 60초 주기 DB 기준 수렴 |

- 입장 정책: 화면상의 대기열 없이 초과분 반려.
- 보정 판단: 최근 선점 복원에 따른 오버셀 위험을 피하기 위한 보류.
- 보정 범위: 60초 주기 처리와 최근 5분 복원 보류를 함께 설명. 모든 불일치의 60초 내 해소 보장으로 해석하지 않음.

- 기술: Spring Boot, gRPC/C++, Prometheus, Grafana.
- 제공 정보: 실시간 여객 위치, 인원 수, 예상 대기시간.
- 합류 당시 문제: 기본 통계만으로 예측 성능 평가 어려움, 고객사 기준에 맞는 개선 지연, C++ 중계 서버 간헐적 종료.

### 메트릭 수집과 분석 흐름

```text
LiDAR 데이터 서버
  -> gRPC -> C++ 데이터 중계 서버
  -> REST API -> Backend
  -> 메트릭 선별과 산출
       -> Prometheus -> Grafana
       -> CSV 로깅 -> Python 분석 -> 결과 리포트
```

위 흐름은 PDF 도식의 표현이다. gRPC의 요청 시작 주체, RPC 유형, REST 호출 방향과 상세는 코드 확인이 필요하다.

### 핵심 개선과 성과

| 사례 | 문제 | 해결 | 성과 |
| --- | --- | --- | --- |
| 실시간 메트릭 분석 | 예측 성능 평가와 개선 지점 파악 한계 | 핵심 메트릭과 수집 범위 확장, Prometheus 및 Grafana 시각화, Python CSV 리포트 자동화 | 분석 파이프라인 구축, 분석 및 개선 시간 80% 단축 |
| C++ 중계 서버 안정화 | 프로세스 메모리 누수와 간헐적 종료 | Visual Studio 누수 지점 확인, Backend 메모리 모니터링과 이상 시 자동 재시작 | 프로세스 메모리 안정화, 간헐적 종료 해소 |
| 로직 통합과 객체 수명 | service와 FE에 분산된 로직, 객체 누적 | 도메인 엔티티로 로직 이동, 계산 및 집계 전담 클래스, 객체 TTL | 메모리 70% 감소, 코드량 50% 감소 |

- 수치 구분: 메모리 70%와 코드량 50%는 세 번째 사례의 성과.
- 원문 범위: 이 페이지에는 약 2,000만 건과 40초에서 1.5초의 조회 개선 수치 미기재.
- 추가 자료: [이력서 LiDAR](resume-reference.md#lidar), [gRPC 개념 정리](lidar-grpc.md), [측정 표현 차이](README.md#differences).

## AI 워크플로우

원문: 13~14쪽.

- 구분: 개인 프로젝트, 2026.
- 기술: AI Agent, GitLab REST API/WebHook, KakaoWork, Git.

### 사례 1: 사내 프로젝트 개선 루프

원문: 13쪽.

- 목표: 코드 리뷰와 작업 배분 자동화를 통한 팀 생산성 개선.
- 연동: LLM과 GitLab, GitLab과 카카오워크.
- 원칙: 사람의 확인과 승인을 거친 항목의 다음 단계 진행.

```text
코드 리뷰
  -> 초안 검토 및 승인 -> GitLab REST API 이슈 발행
  -> GitLab WebHook 및 카카오워크 팀 알림
  -> 이슈 가져오기, 심각도 순 작업 목록
  -> 범위와 계획 승인 -> 구현과 검증
  -> 결과의 다음 코드 리뷰 반영
```

| 단계 | 자동화 역할 | 사람의 역할 |
| --- | --- | --- |
| 코드 리뷰 | 품질, 보안, 버그, 빌드 점검, 파일과 라인 근거, 초안 | 결과와 우선순위 검토 |
| 이슈 발행 | 승인 항목 API 발행 | 발행 대상 승인 |
| 작업 착수 | 계획 및 구현 제안, 승인 후 실행 | 범위와 계획 승인 |

성과:

- 이슈 등록과 작업 배분의 승인 기반 처리.
- 리뷰 결과와 개발 진행의 채널 공유.
- 파일과 라인 근거 및 승인된 변경의 실행 이력 보존.

### 사례 2: 개발 작업 공통 흐름

원문: 14쪽.

- 문제: 세션 임시 목록의 선정 근거와 진행 상태 소실.
- 접근: 설계와 계획 우선, 단계별 소단위 계획과 검증 반복.
- 상태 관리: 저장소 문서와 Git 이력을 실행 상태의 단일 기준으로 사용.

```text
분석과 설계
  -> 작업 목록 생성
  -> 다음 작업 선정
  -> 계획 승인
  -> 구현과 테스트
  -> 기록과 마감
  -> 다음 작업
```

| 작업 규칙 | 원문 내용 |
| --- | --- |
| 작업 목록 우선 생성 | Task_Checklist를 실행 상태의 단일 기준으로 적용 |
| 계획과 승인 우선 | 계획 승인 전 구현 금지, 커밋 메시지 사전 승인 |
| 상태의 단일 기준화 | 세션 임시 목록 대신 Task_Checklist와 Git 이력 |
| 테스트 범위 | 핵심 비즈니스 로직 중심 |
| 소단위 커밋 | 관심사별 변경 분리 |
| Phase 검토 | 결과 문서 검토와 작업 목록 마감 |

위 표는 PDF에 소개된 워크플로우의 내용이며, 이 저장소에 대한 새로운 실행 지시가 아니다.

성과:

- 세션 간 맥락 복원: 선정 근거와 진행 상태의 저장소 확인.
- 일관된 실행 기준: 계획, 승인, 검증 순서 고정.
- 단계별 완성도: 계획과 검증을 거치는 소단위 반복.

PDF에는 생산성의 정량 측정값이나 실제 이슈 사례가 기재되어 있지 않다. 면접 답변에서 별도 성과 수치를 추가하려면 실제 자료를 확인한다.
