## 답변 원칙

1. **상황 → 본인 역할과 판단 → 검증 → 결과 → 한계** 순서로 말한다.
2. 자기소개에서는 강점을 보여 주는 수치 하나만 사용한다. 나머지 수치는 후속 질문에서 측정 조건과 함께 설명한다.
3. 개인 프로젝트의 부하 테스트 결과를 실서비스 성과처럼 말하지 않는다. 서로 다른 실험의 수치도 합쳐 말하지 않는다.
4. 팀의 성과와 본인이 직접 설계·구현·측정한 부분을 구분한다.

아래 형식으로 답변을 추가한다. 답변이 검증되기 전에는 수치나 구조를 확정적으로 쓰지 않는다.

### Q08

**프로파일·환경변수·Docker Compose를 어떻게 나눠 사용했나요?**

[질문 목록](questions.md#2-실무-프로젝트)

### 모범 답변 초안

프로파일은 개발·운영처럼 환경에 따른 애플리케이션 설정을 선택하는 데 사용하고, 환경변수는 현장마다 다른 주소나 설정값을 전달하는 데 사용합니다. Docker Compose는 각 서비스의 이미지, 네트워크, 볼륨과 실행 구성을 관리합니다. 이렇게 나누면 애플리케이션 코드를 바꾸지 않고 현장별 설정을 적용할 수 있습니다.

- **확인 필요:** 실제 프로파일 구분과 환경변수 예시, 비밀값의 보관·전달 방식, 내부망의 이미지 반입 절차. 같은 이미지를 모든 현장에 사용했는지도 확인.
- **참고:** [Spring Boot 프로파일](https://docs.spring.io/spring-boot/reference/features/profiles.html), [Compose 환경변수 전달](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/). `.env`에 적는 것만으로 컨테이너에 전달되지는 않으므로 `environment` 또는 `env_file` 등의 연결 설정 필요.

배포 전에 이전 이미지 버전과 설정을 확보하고, 새 버전의 실행 상태와 로그를 확인하겠습니다. 문제가 있으면 이전 이미지와 설정으로 되돌린 뒤 서비스가 정상 동작하는지 확인하겠습니다. 다만 DB 구조나 데이터까지 변경했다면 이미지 복귀만으로 해결되지 않을 수 있으므로, 이전 버전과의 호환성과 데이터 복구 절차도 함께 확인하겠습니다.

- **확인 필요:** 당시 실제 롤백 구성과 경험, 이미지 버전 관리, 현장 담당자의 복구 절차. 위 답변은 복구 방안이며 실제 수행 이력으로 표현하지 않음.

### Q11

**LiDAR 화면 조회 성능**

> LiDAR 통계 차트 화면은 결과가 표시되기까지 40초대가 걸렸습니다. 원인은 API 구성과 SQL의 인덱스 미활용, 두 가지였습니다. 차트 조회 API가 엑셀 출력용 데이터까지 함께 반환했고, DB 조회 4회 중 중복도 있었습니다. 차트와 엑셀 API를 분리하고 중복 조회를 제거해 쿼리 실행을 2회로 줄였습니다. SQL에서는 비교 대상 컬럼에 적용된 날짜 함수를 제거하고, 동등 조건 컬럼을 앞에, 날짜 범위 조건 컬럼을 뒤에 두도록 복합 인덱스 순서를 바꿨습니다. 조건별 데이터 분포와 실행 계획도 확인했습니다. 그 결과 화면에 결과가 표시되기까지의 시간이 약 1.5초로 줄었습니다.

- **사용자가 확인한 사실:** 차트 API와 엑셀 출력 API 분리, 중복 조회 제거로 DB 조회 4회→2회, 날짜 함수 조건 수정, 복합 인덱스의 동등 조건 컬럼 우선·날짜 범위 조건 컬럼 후순위, 화면 기준 40초대→약 1.5초.
- **다시 확인할 사실:** 화면 시간의 측정 시작·종료 시점과 반복 횟수, API 응답 데이터의 실제 감소량, 날짜 조건식의 변경 전후 형태, 인덱스 컬럼 구성과 실행 계획의 전후 차이.
- **표현 주의:** '선택도가 높은 컬럼부터'라는 일반 규칙으로 설명하지 않는다. 이 쿼리에서는 동등 조건을 앞에, 날짜 범위 조건을 뒤에 두어 복합 인덱스의 탐색 범위를 좁힌 것으로 설명하고 실행 계획으로 뒷받침한다. 각 개선이 전체 시간 중 몇 초씩 기여했는지 따로 측정하지 않았다면 나눠 주장하지 않는다.
- **후속 질문으로 분리:** 다른 출처 데이터의 보정 조인은 Q35로 다룬다. 이 작업이 화면 시간 개선에 직접 기여했는지는 확인되지 않았으므로 `40초대→약 1.5초`의 원인으로 합쳐 말하지 않는다. MariaDB 프로시저·사용자 변수의 사용 목적도 별도로 정리한다.

### Q12

**복합 인덱스의 컬럼 순서**

> 기존 복합 인덱스의 컬럼 순서가 이 조회의 조건과 맞지 않았습니다. 동등 조건 컬럼을 앞에 두고 날짜 범위 조건 컬럼을 뒤에 두면 앞쪽 조건으로 찾은 범위를 날짜 조건으로 더 좁힐 수 있습니다. 조건별 실제 데이터 분포와 `EXPLAIN`을 확인하며 해당 쿼리에 맞게 순서를 조정했습니다.

- **구분할 것:** `WHERE`의 `AND` 조건이나 `INNER JOIN`의 `ON` 조건을 SQL 문장 앞에 적는 것만으로 먼저 실행되지는 않는다. 내부 조인 순서와 조건 적용 시점은 옵티마이저가 정한다. 반면 복합 인덱스의 컬럼 순서는 인덱스의 정렬과 탐색 범위에 영향을 준다.
- **일반화하지 않을 것:** 선택도가 높은 컬럼을 무조건 앞에 두는 규칙은 없다. 특히 모든 조건이 동등 비교일 때는 두 컬럼의 순서를 바꿔도 해당 쿼리가 둘 다 활용할 수 있다. 범위 조건, 다른 조회의 인덱스 접두부 사용, 정렬, 실제 데이터 분포와 실행 계획까지 고려한다.
- **검증 근거:** 변경 전후의 인덱스 정의, `EXPLAIN`의 사용 키와 예상 행 수, 같은 조건의 화면 조회 시간을 확인한다. 기록이 없는 값은 면접에서 만들어 말하지 않는다.
- **참고:** [MariaDB 복합 인덱스 설계](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/optimization-and-indexes/building-the-best-index-for-a-given-select), [MariaDB 옵티마이저의 조인·조건 처리](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizer/optimizer-trace/optimizer-trace-guide)

### Q13

**화면 조회 시간이 40초대에서 1.5초로 개선됐다는 수치는 어떻게 측정했나요?**

[질문 목록](questions.md#2-실무-프로젝트)

### 모범 답변

이 수치는 사용자가 화면에서 조회 결과를 확인하기까지 걸린 시간입니다. 차트와 엑셀 API 분리, 중복 조회 제거, SQL과 인덱스 수정이 합쳐진 결과이므로 특정 쿼리나 인덱스만의 개선 수치로 설명하지 않습니다. 각 변경이 몇 초씩 줄였는지는 별도로 측정하지 않았습니다.

- **확인 필요:** 측정 시작·종료 동작, 사용 도구, 전후 조회 조건·데이터량·환경, 캐시 상태, 반복 횟수. 확인 전에는 동일 조건의 반복 측정이나 평균값이라고 주장하지 않음.

### Q14

### Q19

실시간 영상 메타데이터를 생산하는 쪽과 사용하는 쪽을 분리하고, 전송 형식을 공통화하려는 목적이었습니다. Kafka는 데이터를 받아 두고 Consumer가 처리하도록 연결하는 데, Avro는 데이터 구조를 스키마로 정의하는 데 사용했습니다. Kafka의 성능을 벤치마크하고 데이터 명세와 Producer·Consumer 모듈을 만들어 다른 사내 프로젝트에서도 재사용하도록 했습니다.

- **참고:** [Kafka 설계](https://kafka.apache.org/41/design/design/), [Avro 스키마 해석 규칙](https://avro.apache.org/docs/1.12.0/specification/).

## 3. 개인 프로젝트 기술 검증

### Q22

**같은 좌석에 1,000명이 몰렸을 때 한 명만 성공하는 구조를 설명해 주세요.**

[질문 목록](questions.md#3-개인-프로젝트-기술-검증)

### 모범 답변

Redis Set에서 해당 좌석을 SREM으로 제거한 요청만 DB 예매 단계로 진행합니다. 같은 좌석은 한 요청만 제거할 수 있고, 나머지는 409로 실패합니다. MySQL에서는 좌석 상태를 변경하고 @Version으로 동시 변경 충돌을 감지하며, DB 처리까지 성공해야 예매가 성립합니다. 단일 좌석에 1,000명이 경합하는 실험을 3회 실행해 성공 1건과 초과 판매·중복 0건을 확인했습니다.

- **핵심:** Redis는 DB 진입 제한, MySQL은 예약 원장, @Version은 동시 변경 충돌 감지.
- **근거:** [KTX 설계와 실측](../content/02-ktx-ticketing.md#예매-요청-경로). 입장 초과 429와 좌석 선점·버전 충돌 409 구분.

### Q23

**Redis 선점을 꺼도 초과 판매가 0이었다면 Redis는 왜 필요한가요?**

[질문 목록](questions.md#3-개인-프로젝트-기술-검증)

### 모범 답변

같은 좌석을 얻을 수 없는 요청까지 DB에 들어가 충돌 처리하는 비용을 줄이기 위해서입니다. Redis 선점이 없으면 여러 요청이 DB 조회와 변경을 시도하지만, 선점이 있으면 앞에서 실패한 요청은 DB에 들어가지 않습니다. OFF·ON 실험에서는 둘 다 초과 판매가 0이었고, reserve 응답 시간 중앙값은 약 1.2초에서 0.29초로 줄었습니다. 이 결과로 DB 앞에서 경합 요청을 걸러내는 효과를 확인했습니다.

- **표현 주의:** 낙관적 락과 비관적 락의 성능 비교 결과와 구분. Redis 도입 효과를 낙관적 락의 우월성 근거로 사용하지 않음.
- **근거:** [원자 선점 OFF·ON 비교](../content/02-ktx-ticketing.md#beforeafter-대조-실험). reserve 응답 시간과 전체 예매 완료 시간 구분.

### Q24

**Redis 선점 후 DB 트랜잭션이 실패하면 어떻게 하나요?**

[질문 목록](questions.md#3-개인-프로젝트-기술-검증)

### 모범 답변

DB 롤백만으로 Redis 선점이 복구되지는 않으므로 DB를 기준으로 두 저장소를 보정합니다. 60초마다 비교해 DB에서 사용 중인 좌석이 Redis 잔여석에 있으면 제거합니다. 반대로 Redis에서 사라진 좌석을 복원할 때는 아직 DB 처리가 진행 중일 수 있어 최근 5분 선점의 복원을 보류합니다. 좌석이 잠시 적게 보이는 비용을 감수하고 성급한 재선점을 막는 선택입니다.

- **확인 필요:** 실패 직후 복원·재시도 분기와 선점 시각 기록 방식. 5분 유예의 근거와 장기 실행 트랜잭션 처리.
- **근거:** [불일치 보정 정책](../content/02-ktx-ticketing.md#4-redis와-db-불일치-보정-되돌리는-쪽이-더-위험하다). 시간 유예만으로 Redis·DB 갱신의 원자성이 보장되지는 않음.

### Q25

**입장 제어에서 왜 대기열 대신 429 즉시 반려를 선택했나요?**

[질문 목록](questions.md#3-개인-프로젝트-기술-검증)

### 모범 답변

목표가 서버가 감당할 수 있는 동시 예매 세션을 제한하는 것이어서 활성 세션 상한을 두고 초과 요청은 429로 반려했습니다. 대기 순서와 재입장까지 관리하는 대기열은 구현 범위에 넣지 않았습니다. 부하 실험을 바탕으로 K=100을 설정했고, 제어를 켰을 때 초과분 85.4%를 반려하며 dropped iteration을 0으로 줄였습니다. 대신 사용자의 입장 순서를 보장하지 못하고 재시도가 필요하다는 한계가 있습니다.

- **확인 필요:** K 후보별 지연·처리량과 선택 근거, 클라이언트 재시도 정책. 처리량 약 189 TPS를 동시 세션 100개로 직접 환산하지 않음.
- **표현 주의:** 반려 응답을 포함한 낮은 p95를 예매 성공 요청의 지연으로 설명하지 않음.
- **근거:** [입장 제어 실측](../content/02-ktx-ticketing.md#beforeafter-대조-실험).

### Q26

**조회 캐시의 TTL과 single-flight는 각각 어떤 문제를 해결하나요?**

[질문 목록](questions.md#3-개인-프로젝트-기술-검증)

### 모범 답변

TTL 1초 캐시는 같은 조회의 결과를 잠시 재사용해 반복적인 DB 집계를 줄입니다. 하지만 만료 직후 요청이 몰리면 여러 요청이 동시에 다시 집계할 수 있습니다. single-flight는 같은 키의 재계산을 하나로 모아 이때의 중복 작업을 막습니다. 조회 캐시 실험에서는 이 구성을 적용해 p95를 8~9초에서 약 26ms로 줄였습니다.

- **확인 필요:** single-flight의 적용 범위와 대기·실패 처리. 단일 프로세스의 중복 억제가 여러 인스턴스 전체에도 적용되는지는 별도 확인.
- **표현 주의:** 조회 캐시의 잔여석 정보와 DB 예매 확정 구분. 실측은 캐시와 single-flight를 함께 적용한 결과.
- **근거:** [조회 캐시와 single-flight](../content/02-ktx-ticketing.md#2-조회-캐시-스탬피드-방어-single-flight).

### Q27

**단일 좌석 1,000명 경합과 833~863 TPS는 같은 실험인가요?**

[질문 목록](questions.md#3-개인-프로젝트-기술-검증)

### 모범 답변

서로 다른 실험입니다. L1은 한 좌석에 요청을 집중해 성공 1건과 초과 판매·중복 0건을 확인하는 정합성 실험입니다. L2는 1,000 VU에서 예매 경로의 처리량과 지연을 보는 실험으로, 3회 측정한 처리량이 833~863 TPS이고 p95가 348~408ms였습니다. TPS를 단일 좌석의 성공 건수나 초당 예매 확정 건수로 바꿔 설명하지 않습니다.

- **확인 필요:** L2의 좌석·사용자 분포, 요청 순서, TPS의 집계 대상과 성공·실패 응답 비율.

### Q28

### Q35

**대용량 데이터 보정과 조인**

> LiDAR 프로젝트에서는 다른 출처의 데이터를 활용해 기존 데이터를 보정하는 작업이 자주 있었습니다. 이 과정에서 데이터가 많은 테이블끼리 조인해야 했기 때문에, 조인과 조회 조건에 맞는 인덱스를 활용하지 않으면 작업 비용이 크게 늘어났습니다. 이 경험을 통해 복합 인덱스가 실제 조회 경로에서 어떻게 쓰이는지 더 깊이 이해하게 됐습니다.

- **사용자가 확인한 사실:** 다른 출처 데이터를 통한 기존 데이터 보정, 대용량 테이블 간 조인, 인덱스 활용의 중요성. 조회 API 개선과 구분되는 학습·실무 맥락이다.
- **다시 확인할 사실:** 데이터 출처와 보정 기준, 테이블·조인 키, 기존·변경 인덱스, 실행 계획, 실제 처리 시간 또는 읽은 행 수. 확인 전에는 특정 최적화나 성과 수치를 덧붙이지 않는다.

### Q36

**인덱스의 쓰기·저장 공간 비용과 검증**

> 당시에는 실행 계획과 화면 조회 시간 개선을 확인했고, 쓰기 성능과 공간 변화까지 정량적으로 측정하지는 못했습니다. 지금 다시 한다면 실시간 데이터 입력 지연과 처리량, 보정 UPDATE 작업 시간, 인덱스 크기를 비교하겠습니다. 기존 인덱스 제거 여부도 개선 대상 쿼리뿐 아니라 다른 조회가 사용하는지 확인한 뒤 결정하겠습니다.

- **확인된 범위:** 쓰기 성능과 저장 공간 지표는 측정하지 않았다. 화면 시간 개선은 API·SQL 변경이 합쳐진 결과이며, 인덱스만의 효과나 쓰기 비용을 검증한 수치가 아니다.
- **아직 확인할 사실:** 기존 인덱스를 제거하고 새 순서로 교체했는지, 기존·신규 인덱스를 함께 유지했는지.

| 확인할 지표 | 전후 비교 목적 |
| --- | --- |
| 입력 완료 지연·초당 저장 건수·적체 | 같은 입력량에서 실시간 데이터 저장이 느려지거나 밀리지 않는지 확인 |
| 보정 UPDATE 작업 시간·초당 보정 건수 | 동일한 보정 대상과 조건에서 쓰기 작업이 느려지지 않는지 확인 |
| 개별 조회·조인 시간과 실제 읽은 행 수 | 화면 전체 시간과 구분해 인덱스의 탐색량 감소를 확인 |
| 인덱스별·전체 인덱스 크기 | 인덱스 추가 또는 교체 후 저장 공간 변화 확인 |

- **교체한 경우:** 같은 컬럼의 순서를 바꿔 인덱스 하나를 교체했다면 인덱스 개수를 늘린 경우와 비용이 다르다. 그러나 쓰기 성능이 그대로라고 단정하지 않는다. `(날짜, 상태)`를 `(상태, 날짜)`로 바꿀 때 날짜만 조회하는 기존 쿼리 등 다른 사용 경로와 제약조건 의존성을 확인한다.
- **함께 유지한 경우:** 각 인덱스를 필요로 하는 조회가 있는지 확인한다. 같은 컬럼이어도 순서가 다르면 용도가 다를 수 있다. 두 인덱스를 유지할 필요가 있다면 추가 쓰기·공간 비용을 비교하고, 기존 인덱스가 불필요하면 제거한다.
- **측정 방법:** 같은 데이터량·부하 조건으로 비교하고 쓰기는 커밋까지 포함한 완료 시간으로 잰다. `EXPLAIN`의 행 수는 추정값이며, `ANALYZE FORMAT=JSON`은 실제 실행 통계를 제공한다. UPDATE·DELETE에도 사용하면 실제 데이터가 변경되므로 테스트 환경에서 수행한다. 인덱스 크기는 `mysql.innodb_index_stats`의 `size` 페이지 수 등을 확인한다.
- **제거 전 확인:** MariaDB 10.6 이상에서 `IGNORED`로 기존 인덱스를 옵티마이저가 사용하지 않도록 해 조회의 영향을 확인할 수 있다. 이 상태에서도 인덱스는 유지·갱신되므로 삭제 후 쓰기 비용 감소를 측정하는 방법은 아니다.
- **참고:** [실행 통계](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/analyze-and-explain-statements/analyze-format-json), [인덱스 통계](https://mariadb.com/docs/server/reference/system-tables/the-mysql-database-tables/mysql-innodb_index_stats), [Ignored Indexes](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/optimization-and-indexes/ignored-indexes)
