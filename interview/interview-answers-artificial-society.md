# 아티피셜소사이어티 백엔드 개발자 면접 답변

[예상 질문과 자기소개](interview-questions-artificial-society.md)

질문 문서의 번호에 맞춰 답변을 정리한다. 확인되지 않은 경험과 수치는 추가 확인 항목으로 구분한다.

## Q01

**가장 주도적으로 개발한 백엔드 프로젝트를 설명해 주세요.**

### 주 답변 초안: LiDAR

> 제가 백엔드 개선을 주도한 사례는 김포공항 LiDAR 프로젝트입니다. LiDAR 데이터를 기반으로 실시간 여객 위치와 인원 수, 예상 대기시간을 제공하는 시스템입니다. LiDAR 데이터 서버에서 gRPC로 데이터를 받는 C++ 중계 서버가 있고, Spring Boot 백엔드와 REST API로 연계하는 구조였습니다.
>
> 저는 백엔드의 비즈니스 로직 정리와 예측 성능 분석 환경 구축, 중계 서버의 운영 안정성 개선을 맡았습니다. 합류 당시에는 기본 통계만으로 예측 성능을 평가하기 어려웠고, 비즈니스 로직이 서비스 계층과 프론트엔드에 분산돼 있었습니다.
>
> 분산된 로직을 도메인 엔티티와 계산 및 집계 전담 클래스로 정리하고, 핵심 메트릭을 정의해 Prometheus와 Grafana로 확인할 수 있도록 했습니다. 분석 리포트도 자동화해 예측 성능을 평가하고 개선할 수 있는 흐름을 마련했습니다. C++ 중계 서버의 메모리 누수 지점을 확인하고, 백엔드에 메모리 모니터링과 이상 시 자동 재시작 기능도 추가했습니다.

- **답변 근거:** [LiDAR 콘텐츠 원천](../content/03-lidar.md).
- **기여 범위:** 기존 시스템 합류 후 개선 담당. 초기 아키텍처 전체 설계 및 프로젝트 총괄과 구분.
- **답변 초점:** 서비스 구조, 본인 책임, 로직 정리와 관측 및 운영 개선.
- **성능 상세:** API와 SQL 병목 분석 및 조회 시간 수치는 [Q02](#q02)에서 설명.
- **추가 확인:** 각 개선에서 본인이 직접 결정하고 구현한 범위, 팀원과의 역할 분담.
- **추가 확인:** 가장 어려웠던 의사결정, 당시 비교한 대안과 선택 기준.
- **추가 확인:** 다시 만든다면 바꿀 점과 당시 제약의 연결.

어려웠던 의사결정은 실제 당시 고민을 확인한 뒤 보완한다. JD에 맞추기 위해 경험의 난도나 책임 범위를 바꾸지 않는다.

### 대체 답변 초안: Tag2Now

서비스 전체를 가장 주도적으로 만든 경험을 강조할 때 사용한다. 회사의 실무 프로젝트로 범위를 한정한 질문에는 LiDAR로 답한다.

> 개인 프로젝트 중 가장 주도적으로 개발한 서비스는 Tag2Now입니다. 철권 태그2 커뮤니티에서 활성 유저와 매칭 정보를 한눈에 확인하기 어렵다는 문제를 해결하기 위해 만들었습니다. 문제 정의부터 백엔드 구현, AWS 배포와 운영까지 직접 맡았습니다.
>
> 가장 어려웠던 부분은 공식 SDK와 게임별 호출 명세가 없는 외부 서버와 연동하는 일이었습니다. 오픈소스 서버 구현을 분석해 바이너리 프로토콜을 파악하고, Python 클라이언트를 구현한 뒤 단위 테스트와 통합 테스트로 검증했습니다.
>
> 운영 과정에서는 서비스 규모에 비해 인프라 비용과 관리 부담이 커서 ECS Fargate에서 Lightsail과 Docker Compose로 전환했습니다. 단일 서버 장애 위험을 감수하는 대신 운영 복잡도와 비용을 낮춘 선택이었습니다. 이후 실제 사용자 제보를 받아 오류와 기능을 개선했습니다.

- **답변 근거:** [Tag2Now 콘텐츠 원천](../content/01-tag2now.md).
- **JD 연결:** AWS 운영, 분석적 문제 해결, 사용자 피드백 기반 개선.
- **역량 보완:** Java와 Spring 및 관계형 DB 역량은 LiDAR나 KTX 경험으로 설명.
- **추가 확인:** 다시 만든다면 바꿀 점. 단일 서버의 백업과 복구 절차 검토는 후보이며, 실제 준비 수준 확인 후 답변 확정.

### 사례 선택과 JD 연결

이 회사에서는 LiDAR의 실무 백엔드 개선 경험을 주 답변으로 준비한다. Tag2Now는 서비스 전체를 주도한 경험을 보여주지만, 외부 서버의 바이너리 프로토콜 분석은 Spring Boot API 개발과 DB 최적화 역량을 직접 보여주는 사례로는 거리가 있다. 기술적 난도와 JD 적합성을 구분해 선택한다.

| 사례 | 강조할 역량 | 활용 질문 |
| --- | --- | --- |
| LiDAR | Spring Boot 로직 정리, 메트릭 분석 환경, 운영 안정성 개선 | Q01의 실무 개선 주도 경험, Q02의 API와 SQL 성능 개선 |
| Tag2Now | 문제 정의부터 구현과 운영까지의 주도성, AWS 운영, 사용자 피드백 | 서비스 전체 개발과 운영 경험 |
| KTX 티켓팅 | Spring Boot와 MySQL 기반 동시성 설계, 부하 검증 | 동시성 처리와 성능 검증 경험 |

- **JD 근거:** [채용 공고](https://www.wanted.co.kr/wd/378144)의 Spring Boot REST API 개발, DB 설계와 최적화, AWS 인프라 운영, 분석적 문제 해결 요구.
- **기여 범위:** 프로젝트 전체 총괄과 본인이 주도한 백엔드 개선의 구분.
- **경험의 경계:** KTX 개인 부하 테스트와 실서비스 트래픽 운영의 구분.
- **답변 배분:** Q01은 서비스 구조와 담당 범위 및 개선 주도 경험, Q02는 조회 병목의 원인과 수정 및 검증.

## Q02

**실제로 성능 문제를 발견하고 개선한 경험이 있나요?**

### 답변 초안: LiDAR 통계 화면 조회

> 김포공항 LiDAR 프로젝트에서 통계 차트 화면의 결과 표시까지 40초대가 걸리는 문제를 개선했습니다. 원인은 API 구성과 SQL의 인덱스 미활용, 두 가지였습니다.
>
> 차트 조회 API가 엑셀 출력용 데이터까지 함께 반환했고, DB 조회 4회 중 중복도 있었습니다. 차트와 엑셀 API를 분리하고 중복 조회를 제거해 DB 조회를 2회로 줄였습니다. SQL에서는 비교 대상 컬럼에 적용된 날짜 함수를 제거하고, 동등 조건 컬럼을 앞에, 날짜 범위 조건 컬럼을 뒤에 두도록 복합 인덱스 순서를 조정했습니다.
>
> 조건별 데이터 분포와 실행 계획을 확인하며 개선했고, 그 결과 화면에서 결과를 확인하기까지의 시간을 약 1.5초로 줄였습니다. 다만 당시에는 인덱스 변경에 따른 쓰기 성능과 저장 공간 변화까지 정량적으로 측정하지는 못했습니다. 다시 검증한다면 실시간 데이터 입력 지연과 처리량, 보정 작업 시간, 인덱스 크기도 함께 비교하겠습니다.

- **답변 근거:** [확인된 조회 개선 경험](answers.md#q11), [복합 인덱스 선택 근거](answers.md#q12), [쓰기 및 저장 공간 검증의 한계](answers.md#q36).
- **수치 범위:** SQL 단독 실행 시간이 아닌 화면 결과 표시 시간. API와 SQL 개선의 합산 결과.
- **추가 확인:** 최초 발견 경로와 병목을 구분한 조사 순서 및 당시 로그나 측정 기록.
- **추가 확인:** 시간 측정 시작과 종료 시점, 반복 횟수, 조회 조건과 데이터량 및 캐시 영향.
- **추가 확인:** 변경 전후 조건식과 인덱스 정의, 실행 계획, 기존 인덱스 교체 또는 유지 여부.

## Q03

**여러 DB 변경이 모두 성공하거나 모두 취소돼야 한다면, `@Transactional`을 어느 메서드에 붙이겠어요?**

### 답변 초안: 설계 기준

> 먼저 작업이 끝났을 때 지켜야 할 업무 규칙과, 실패했을 때 남아도 되는 상태를 정하겠습니다. 그 기준으로 함께 커밋돼야 하는 DB 변경을 묶고, 여러 Repository를 호출하더라도 하나의 업무가 완결되는 서비스 메서드에 경계를 두겠습니다. 변경 여부를 결정하는 DB 상태 조회도 함께 고려하겠습니다.
>
> 외부 API 실패 시 앞선 DB 변경도 취소해야 하고, 호출에 그 변경이나 잠금이 필요하다면 DB 트랜잭션을 유지한 채 호출하는 선택을 하겠습니다. 실패 응답을 롤백 대상 예외로 처리하고 네트워크 타임아웃과 연결 및 락 점유 비용을 검토하겠습니다. 다만 외부 API의 성공 뒤 DB 커밋이 실패하거나, 타임아웃으로 외부 처리 결과를 알 수 없는 상황은 로컬 트랜잭션만으로 해결되지 않습니다.
>
> 반대로 AI 실패와 관계없이 제출을 보존해야 한다면 제출과 처리 대기 기록을 함께 커밋하고, AI 호출과 결과 저장을 분리하겠습니다. 외부 호출 분리를 일괄 적용하기보다 업무의 실패 정책에 따라 경계를 선택하고, 정합성을 유지할 수 있는 범위에서 형식 검증과 장시간 계산 등을 밖으로 옮기겠습니다.

- **설계 자료:** [트랜잭션 범위를 결정하는 기준](spring-transactions.md#면접-질문의-설계-기준).
- **답변 상태:** 설계 질문에 대한 가정형 초안. 실무 적용 경험을 가정하지 않음.
- **경계 분리의 조건:** 정합성 유지. 짧은 트랜잭션을 위해 함께 커밋돼야 하는 변경까지 분리하지 않음.
- **외부 호출 순서:** 선행 DB 변경과 잠금에 의존하지 않는 호출은 DB 트랜잭션 시작 전 수행 가능성 검토. 외부 성공과 DB 커밋의 원자성은 별도 문제.
- **외부 처리 한계:** 로컬 DB 롤백과 외부 작업 취소의 구분. 결과 조회와 멱등성 또는 보상 처리 필요성 검토.
- **동시성 구분:** 상태 조회와 변경을 묶는 것만으로 경쟁 상황 해결 불가. 업무 규칙에 맞는 격리 수준, 락, 버전 검증 또는 DB 제약 검토.
- **꼬리 질문:** 프록시와 내부 호출 및 롤백 규칙은 선언한 경계의 실제 적용 여부를 설명할 때 사용.
- **추가 확인:** 본인 코드의 `@Transactional` 위치와 호출 경로, 사용한 트랜잭션 매니저와 롤백 설정.

### 꼬리 답변: 같은 클래스 내부 호출

> Spring의 기본 프록시 방식에서는 같은 객체 안에서 다른 메서드를 직접 호출하면 프록시를 거치지 않아 내부 메서드의 `@Transactional` 설정이 적용되지 않습니다. 바깥에 트랜잭션이 없으면 내부 선언으로 새 경계가 생기지 않고, 바깥에서 이미 시작했다면 내부 DB 작업은 그 트랜잭션 안에서 실행될 수 있습니다. 내부 메서드에 `REQUIRES_NEW`를 붙여도 직접 호출하면 새 트랜잭션으로 분리되지 않습니다.
>
> 하나의 업무를 묶으려면 외부에서 호출되는 서비스 메서드에 경계를 두고, 다른 경계가 필요하다면 별도 Spring 빈의 프록시를 통해 호출해 전파 설정이 적용되도록 하겠습니다.

- **관련 설명:** [프록시와 같은 클래스 내부 호출](spring-transactions.md#2-프록시와-같은-클래스-내부-호출).
- **외부 API 설계 연결:** 같은 클래스의 다른 메서드로 호출 코드를 옮기거나 어노테이션을 없애는 것만으로 기존 트랜잭션 종료 불가. 호출 흐름 전체의 실제 경계 확인.

### 꼬리 답변: 컨트롤러에서 트랜잭션 메서드를 호출하면

> 컨트롤러가 Spring에서 주입받은 서비스 빈의 `@Transactional` 메서드를 호출하면 서비스 프록시를 거칩니다. 트랜잭션 인터셉터가 매니저를 통해 트랜잭션을 시작하거나 기존 트랜잭션에 참여한 뒤 실제 메서드를 실행하고, 반환이나 예외에 따라 트랜잭션 종료를 처리합니다. 같은 객체 안의 직접 호출과 달리 해당 메서드의 설정이 적용됩니다.

- **관련 설명:** [컨트롤러 호출 경로](spring-transactions.md#컨트롤러에서-트랜잭션-메서드를-호출하면).
- **호출 대상 구분:** 필드와 `this` 문법보다 참조 대상의 프록시 여부가 기준. `this.service.method()`는 주입된 프록시 호출 가능, `this.method()`는 동일 객체 내부 호출.

## Q04

**여러 요청이 동시에 같은 데이터를 수정하는 상황을 어떻게 처리했나요?**

### 주 답변 초안: KTX 티켓팅

> 개인 프로젝트인 KTX 티켓팅에서 여러 사용자가 같은 좌석을 동시에 예매하는 상황을 다뤘습니다. 핵심 규칙은 하나의 좌석에 예매가 정확히 한 건만 확정되는 것이었습니다.
>
> DB에서는 `@Version`을 이용한 낙관적 락으로 같은 버전을 읽은 요청들이 모두 변경에 성공하지 못하도록 했습니다. 다만 같은 좌석으로 요청이 몰리면 DB에서 충돌을 처리하는 비용이 커지기 때문에, 앞단에 Redis Set의 원자 연산을 이용한 좌석 선점을 두어 DB로 넘어가는 경합을 줄였습니다. Redis와 DB는 하나의 트랜잭션이 아니므로 DB를 최종 기준으로 두고, 불일치는 DB 상태를 기준으로 보정했습니다.
>
> 로컬 부하 테스트에서는 동일 좌석에 1,000명이 경합하는 시나리오를 세 차례 실행해 성공 한 건과 초과 판매 및 중복 예매 0건을 확인했습니다. Redis 선점을 끈 실험에서도 초과 판매는 없었습니다. 이 결과로 DB가 정합성을 지키고 Redis 선점은 DB 부하를 줄이는 역할이라고 판단했습니다.

- **답변 근거:** [KTX 티켓팅 콘텐츠 원천](../content/02-ktx-ticketing.md).
- **경험 범위:** 개인 프로젝트, 로컬 Windows의 Docker Compose 환경. 실서비스 피크 트래픽 운영 경험과 구분.
- **검증 범위:** 동일 좌석 경합 시나리오 3회. 모든 장애 상황에서의 정합성 보장으로 확대하지 않음.
- **추가 확인:** `@Version` 적용 엔티티와 트랜잭션 경계, 예매 확정 상태 전이, 충돌 예외 처리 코드.
- **추가 확인:** Redis 선점 성공 후 DB 실패 및 프로세스 종료 시 처리 경로, 보정 대상과 복원 지연 정책.

### 꼬리 답변: 낙관적 락과 비관적 락의 선택 기준

> 충돌 빈도뿐 아니라 충돌했을 때 요청을 실패시켜도 되는지, 다시 처리해야 하는지를 함께 보겠습니다. 낙관적 락은 읽은 버전과 DB 버전을 비교해 충돌한 변경을 실패시킵니다. 같은 좌석 예매처럼 한 요청만 성공하고 나머지는 실패해도 되는 상황에서는 고려할 수 있습니다. 다만 충돌이 많으면 실패한 작업의 비용이 커지므로, 제 프로젝트에서는 앞단 선점으로 경합을 줄였습니다.
>
> 비관적 락은 먼저 잠금을 얻고 상태를 확인한 뒤 변경해야 할 때 고려하겠습니다. 요청을 기다리게 하는 비용과 락 타임아웃, 데드락 가능성을 검토하고, 트랜잭션을 짧게 유지하겠습니다. 충돌이 많다는 이유만으로 비관적 락을 선택하기보다 실패와 대기의 비용을 실제 부하에서 비교하겠습니다.

- **동작 근거:** [Jakarta Persistence 잠금 설명](https://jakarta.ee/learn/docs/jakartaee-tutorial/current/persist/persistence-locking/persistence-locking.html), [MySQL 잠금 조회](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html).
- **선택 이유의 상태:** 현재 구조에 대한 설명. 당시 비관적 락과 비교한 실험 및 의사결정 기록은 확인 필요.
- **재시도 조건:** 낙관적 락 충돌 후 필요하다면 새 트랜잭션에서 최신 상태 재조회 및 업무 조건 재검증. 이미 예매된 좌석은 재시도 대신 실패 처리.
- **락의 한계:** 단일 엔티티 버전 검사만으로 여러 행에 걸친 모든 업무 규칙 보장 불가. 규칙별 DB 제약과 잠금 범위 검토.

### 꼬리 답변: 애플리케이션에서만 제어할 때의 한계

> `synchronized`나 JVM 내부 락은 같은 프로세스 안의 요청만 제어하므로 서버가 여러 대라면 같은 DB 데이터를 동시에 변경할 수 있습니다. 그래서 공유 데이터를 지키는 최종 조건은 DB의 버전 검사나 잠금, 유니크 제약 등에 두겠습니다. Redis 원자 연산도 여러 서버의 요청을 조율할 수 있지만, DB 변경과 원자적으로 묶이지 않는 문제는 별도로 처리해야 합니다.

### 꼬리 답변: 중복 요청과 재시도

> 동시성 제어와 함께, 같은 예매 요청을 다시 받아도 예매가 추가로 생성되지 않도록 멱등성을 설계하겠습니다. 클라이언트가 한 번의 예매 시도에 같은 요청 키를 사용하도록 하고, 서버는 사용자와 작업 범위 및 요청 키를 묶어 DB 유니크 제약으로 중복 처리를 막겠습니다.
>
> 예매 변경과 요청 키 및 결과 기록은 같은 DB 트랜잭션으로 커밋하겠습니다. 응답만 유실된 경우에는 같은 키로 재요청해도 기존 예매 결과를 반환하고, 같은 키에 다른 요청 내용이 들어오면 거절하겠습니다. 동시에 들어온 중복 요청이 아직 처리 중이라면 진행 상태를 알려 재조회를 유도하겠습니다.

- **답변 상태:** 추가 설계안. KTX 프로젝트에 멱등성 키를 구현한 경험으로 말하지 않음.
- **설계 근거:** [AWS 재시도와 멱등성 설계](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).
- **문제 구분:** 서로 다른 사용자의 동일 좌석 경합과 동일 사용자의 동일 작업 재전송.
- **키 운영:** 동일 작업 재시도 시 키 유지, 키 보존 기간과 늦게 도착한 요청 처리 정책 검토.
- **업무 제약:** 요청 키가 달라도 같은 좌석에 활성 예매가 중복 확정되지 않도록 상태 전이와 DB 제약 검토.
- **원자성 범위:** 위 설계는 같은 DB의 변경 기준. Redis 및 외부 서비스 부수 효과는 별도 정합성 설계 필요.

## Q05

**MySQL 쿼리가 느릴 때 어떤 순서로 분석하나요?**

### 주 답변 초안: 분석 순서

> 먼저 느린 SQL과 실제 파라미터, 데이터량, 발생 조건을 확보하겠습니다. API 전체 지연 중 SQL 실행이 차지하는 시간을 구분하고, 쿼리의 실행 빈도와 락 대기, DB 자원 상태도 확인하겠습니다.
>
> 다음으로 `EXPLAIN`에서 테이블 접근 순서와 접근 방식, 실제 선택한 인덱스, 예상 탐색 행 수, 정렬과 임시 테이블 사용을 보겠습니다. 인덱스를 사용한다는 사실만으로 충분하다고 판단하지 않고, 결과에 비해 얼마나 많은 데이터를 읽는지 확인하겠습니다. 필요하면 검증 환경에서 `EXPLAIN ANALYZE`로 실제 행 수와 반복 횟수, 실행 시간을 확인해 예상과 다른 구간을 찾겠습니다.
>
> 원인에 따라 불필요한 조회와 조인을 줄이고, 조건식이 인덱스 탐색을 활용할 수 있는지 검토하겠습니다. 복합 인덱스는 동등 조건과 범위 조건, 조인과 정렬, 다른 조회의 사용 패턴을 함께 보고 결정하겠습니다.
>
> 변경 후에는 같은 데이터와 파라미터 및 부하 조건에서 실행 시간과 탐색량을 비교하고, 결과가 동일한지도 확인하겠습니다. 인덱스 변경이라면 쓰기 성능과 저장 공간, 다른 쿼리에 미치는 영향도 검증하겠습니다.

- **답변 상태:** MySQL 분석 절차에 대한 준비 답변. 모든 도구와 검증 항목을 실무에서 사용한 경험으로 말하지 않음.
- **실행계획 근거:** [MySQL EXPLAIN 출력](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html), [EXPLAIN ANALYZE](https://dev.mysql.com/doc/refman/8.4/en/explain.html#explain-analyze).
- **검증 조건:** 캐시 상태, 반복 횟수, 동시 요청량 구분. API 및 화면 시간과 SQL 단독 시간 분리.
- **추가 확인:** LiDAR에서 사용한 DB 제품과 버전, 당시 수집한 실행계획과 진단 도구. MariaDB 관련 기록을 MySQL 전용 기능 사용 경험으로 바꾸지 않음.

### 실제 경험 연결: LiDAR 통계 조회

> LiDAR 프로젝트에서는 통계 화면의 조회를 개선하면서 중복 DB 조회를 줄이고, 비교 대상 컬럼에 적용된 날짜 함수를 제거했습니다. 복합 인덱스는 동등 조건 컬럼을 앞에, 날짜 범위 조건 컬럼을 뒤에 두도록 조정했고, 조건별 데이터 분포와 실행계획을 확인했습니다.
>
> API 구성과 SQL을 함께 개선한 결과 화면에서 결과를 확인하기까지의 시간이 40초대에서 약 1.5초로 줄었습니다. 이 수치는 SQL 단독 실행 시간이 아니며, 당시 쓰기 성능과 저장 공간 변화까지 정량적으로 측정하지는 못했습니다.

- **경험 근거:** [확인된 조회 개선 경험](answers.md#q11), [복합 인덱스 선택 이유](answers.md#q12), [쓰기와 공간 검증의 한계](answers.md#q36).
- **추가 확인:** SQL 및 인덱스 변경 전후 정의, 실행계획의 사용 키와 예상 행 수 변화, 시간 측정 조건.

### 꼬리 답변: 실행계획에서 확인할 항목

| 항목 | 확인 내용 |
| --- | --- |
| 테이블 및 조인 순서 | 먼저 읽는 데이터와 후속 조인의 입력 규모 |
| `type` | 전체 스캔, 인덱스 범위 탐색, 키 조회 등 접근 방식 |
| `possible_keys`, `key` | 후보 인덱스와 실제 선택한 인덱스의 차이 |
| `key_len`, JSON의 `used_key_parts` | 복합 인덱스의 사용 부분 |
| `rows`, `filtered` | 예상 탐색 행 수와 조건 통과 비율 |
| `Extra` | 추가 정렬, 임시 테이블, 인덱스 조건 처리 등 |
| `EXPLAIN ANALYZE` | 단계별 실제 반환 행 수, 반복 횟수, 실행 시간과 추정값의 차이 |

- **해석 원칙:** `ALL`, `Using filesort`, `Using temporary`의 존재만으로 병목 판정 불가. 처리 데이터량과 실제 비용 확인.
- **값의 구분:** `rows`는 추정 탐색 행 수. `EXPLAIN ANALYZE`의 실제 행 수는 해당 실행 단계의 반환 행 수이며 필터 전후 단계 구분 필요.
- **반복 해석:** `EXPLAIN ANALYZE`의 시간과 행 수는 반복 시 회당 평균값. `loops`와 함께 해석.
- **실행 특성:** `EXPLAIN ANALYZE`는 대상 쿼리를 실제 실행. 무거운 조회의 검증 환경과 실행 조건 검토.

### 꼬리 답변: 복합 인덱스 컬럼 순서

> 예를 들어 학교 ID를 동등 조건으로 조회하고 제출일을 범위 조건으로 조회한다면, `(school_id, submitted_at)`을 후보로 검토하겠습니다. 특정 학교의 데이터 안에서 날짜 범위를 탐색할 수 있기 때문입니다. 다만 선택도가 높은 컬럼을 무조건 앞에 두지는 않겠습니다. 정렬과 다른 조회에서 사용하는 인덱스 접두부, 실제 데이터 분포까지 보고 실행계획과 시간으로 확인하겠습니다.

- **범위 조건:** 일반적인 B-tree 범위 탐색에서 부등호 범위 조건 이후 컬럼은 탐색 구간을 더 좁히는 데 제약. 후속 컬럼의 인덱스 조건 필터링 및 커버링 활용과 구분.
- **모든 조건이 동등 비교인 경우:** 단일 쿼리의 선택도만으로 순서 결정 불가. 다른 조회와 정렬의 활용도 고려.
- **예시 상태:** 교육 서비스에 대한 가정. LiDAR의 실제 컬럼명 및 인덱스 정의와 구분.
- **동작 근거:** [MySQL 복합 키 범위 최적화](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html#range-access-multi-part).

### 꼬리 답변: 인덱스를 추가해도 빨라지지 않는 이유

> 먼저 새 인덱스가 실행계획에서 선택됐는지 확인하겠습니다. 선택되지 않았다면 조건과 인덱스 순서가 맞지 않거나, 컬럼에 적용한 함수나 형 변환 때문에 원하는 탐색을 못 하는지 보겠습니다. 조건에 맞는 데이터가 너무 많거나 통계가 실제 분포와 다르면 옵티마이저가 다른 경로를 선택할 수도 있습니다.
>
> 인덱스를 사용하더라도 읽는 행이 많거나 테이블 행 조회, 정렬과 집계, 반복 조인 비용이 크면 효과가 제한될 수 있습니다. 또한 락 대기나 I/O가 원인이라면 인덱스 추가만으로 해결되지 않을 수 있으므로, 실제 시간이 소비되는 구간을 다시 확인하겠습니다.

- **판단 구분:** 인덱스 미사용과 인덱스 사용 후 비용 과다.
- **함수 조건의 예외:** 함수 인덱스나 인덱스가 있는 생성 컬럼 등의 사용 가능성 및 DB 버전 검토. 모든 함수가 인덱스 활용을 막는다고 단정하지 않음.
- **통계 확인:** 추정과 실제 행 수 차이가 크면 데이터 분포 및 통계 상태 조사. `ANALYZE TABLE` 효과는 실행계획과 시간으로 재확인.
- **기존 인덱스 제거:** 다른 조회와 제약조건의 의존성 확인 후 결정.
