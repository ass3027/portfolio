### 질문내용

LiDAR 조회를 40초에서 1.5초로 개선한 과정을 설명해 주세요.

- 꼬리 질문: 불필요한 쿼리 호출과 쿼리 자체의 병목을 어떻게 구분했나요?

### 내 답변

<!-- 이 아래에 답변을 작성하세요. -->
먼저 브라우저 개발자 도구를 활용해 어떤 api가 느린지 확인했습니다. 그 후 해당 api 안에서 어떤 지점이 병목인지 확인했고 불필요한 쿼리와 느린 쿼리를 확인하였습니다. 불필요한 쿼리는 제거하고 느린쿼리를 explain 키워드를 통해 검토하여 index가 제대로 적용되고 있는지 확인했습니다. index는 사용되고 있었지만 예상 탐색 행이 400만건 대 였습니다. 탐색 범위를 더 줄이기 위해 조건대상 칼럼에 사용된 함수를 제거하고, 동등조건과 범위조건을 고려해서 복합인덱스를 교체하였습니다. 이를 통해 7초대로 줄일 수 있었습니다. 하지만 데이터 수 자체가 많아 그 이상의 개선은 쿼리를 통해 하기 힘들다 판단했고, 월별, 년별 통계는 사전집계 테이블을 도입해 데이터 수 자체를 줄여 1.5초 까지도 줄일 수 있었습니다.

### 개선안

불필요한 DB 조회 제거와 쿼리 개선, 사전집계 도입으로 통계 화면 표시 시간을 약 40초에서 1.5초로 줄였습니다. 브라우저 개발자 도구로 느린 API를 찾고, API 내부에서 불필요한 조회와 느린 SQL을 구분했습니다. EXPLAIN에서는 range 접근의 예상 조회 행 수가 400만 건대인 점을 확인했습니다. 조건 컬럼의 함수를 제거하고 동등 조건과 범위 조건에 맞춰 복합 인덱스를 변경해 약 7초로 줄였습니다. 이후 월별, 연별 통계에 사전집계 테이블을 도입해 조회 시 처리할 데이터량을 줄였습니다.

## Q03 [P1]

[질문과 준비 메모](questions.md#q03)

### 질문내용

대용량 조인 조회에서 복합 인덱스의 컬럼과 순서를 어떻게 정했나요?

- 꼬리 질문: 실제 WHERE, JOIN, ORDER BY 조건을 간단한 쿼리로 설명할 수 있나요?
- 꼬리 질문: 동등 조건과 범위 조건, 정렬, 컬럼 선택도를 어떻게 함께 고려하나요?
- 꼬리 질문: 인덱스가 있어도 사용하지 않거나 읽는 행이 많은 이유는 무엇인가요?
- 꼬리 질문: 기존 인덱스는 유지했나요? 입력·보정 작업과 저장 공간 비용도 측정했나요?

### 내 답변

LiDAR 조회에서는 동등 조건에 사용한 컬럼을 앞에, 날짜 범위 조건 컬럼을 뒤에 두도록 복합 인덱스 순서를 조정했습니다. 동등 조건으로 대상을 좁힌 뒤 날짜 범위를 탐색하려는 목적이었습니다. 선택도가 높은 컬럼을 무조건 앞세우기보다 실제 조회 조건과 데이터 분포를 기준으로 판단했습니다. 변경 후 EXPLAIN으로 인덱스 사용 여부를 확인했습니다.

### 꼬리 질문 1

#### 질문내용

실제 WHERE, JOIN, ORDER BY 조건을 간단한 쿼리로 설명할 수 있나요?

#### 내 답변

실제 SQL 원문과 컬럼명은 확인이 필요합니다. 원리를 설명하는 가상 예시는 다음과 같습니다.

```sql
SELECT m.id, z.name
FROM measurement m JOIN zone z ON z.id = m.zone_id
WHERE m.zone_id = :zone
  AND m.ts >= :from AND m.ts < :to
ORDER BY m.ts;
```

이 경우 measurement의 `(zone_id, ts)`와 zone의 기본 키 `id`를 인덱스 후보로 봅니다. 실제 사용 여부와 정렬 처리는 EXPLAIN으로 확인합니다.

### 꼬리 질문 2

#### 질문내용

동등 조건과 범위 조건, 정렬, 컬럼 선택도를 어떻게 함께 고려하나요?

#### 내 답변

우선 동등 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에 두는 구성을 후보로 잡습니다. 범위 조건 뒤의 컬럼은 탐색 범위를 추가로 좁히는 데 제약이 있어, 정렬까지 인덱스로 처리할 수 있는지 따로 확인합니다. 선택도만으로 순서를 정하지 않고 다른 조회에서 선두 컬럼을 활용하는지도 고려합니다. 최종적으로 실제 데이터 분포와 실행 계획, 응답 시간을 비교해 결정합니다.

### 꼬리 질문 3

#### 질문내용

인덱스가 있어도 사용하지 않거나 읽는 행이 많은 이유는 무엇인가요?

#### 내 답변

조건에 맞는 데이터가 많으면 인덱스와 원본 행을 반복해서 읽는 것보다 전체 스캔이 저렴할 수 있습니다. 선두 컬럼 조건이 없거나 컬럼에 적용한 함수 때문에 인덱스 탐색이 어려운 경우도 있습니다. 인덱스를 사용하더라도 범위가 넓거나 후속 조건이 탐색 범위를 줄이지 못하면 많은 행을 읽습니다. EXPLAIN의 사용 인덱스와 예상 행 수를 확인하고, 필요하면 실제 실행 통계와 비교하겠습니다.

### 꼬리 질문 4

#### 질문내용

기존 인덱스는 유지했나요? 입력·보정 작업과 저장 공간 비용도 측정했나요?

#### 내 답변

기존 인덱스를 유지했는지 교체했는지는 당시 인덱스 정의와 변경 이력을 확인해야 정확히 답할 수 있습니다. 당시에는 실행 계획과 화면 조회 시간 개선을 확인했고, 쓰기 성능과 저장 공간 변화는 정량적으로 측정하지 못했습니다. 다시 검증한다면 같은 조건에서 입력 지연, 보정 UPDATE 시간, 인덱스 크기를 비교하겠습니다. 기존 인덱스 제거 여부도 다른 조회와 제약조건이 사용하는지 확인한 뒤 결정하겠습니다.

외부 분석서버 호출을 분석 요청 저장 트랜잭션에서 분리시키겠습니다. 외부 분석서버 호출이 실패되더라도 분석 요청 기록은 남아야 하기 떄문입니다. 분석 요청 기록 트랜잭션 밖에서 외부 분석서버 호출을 하고 지수 재시도를 이용해서 1차적인 장애 복구를 하겠습니다. 그리고 서버 장애로 인해 호출이 안된 요청들을 별도로 처리하는 복구 로직을 추가하겠습니다.

- 꼬리 질문: Lazy 설정만으로 N+1을 막을 수 있나요? 실행 SQL은 어떻게 확인하나요?
- 꼬리 질문: fetch join, batch fetch, DTO 조회를 어떤 기준으로 선택하나요?

- 꼬리 질문: 깊은 페이지를 조회할 때 offset과 cursor 방식은 어떻게 다른가요?

### 내 답변

<!-- 이 아래에 답변을 작성하세요. -->
먼저 필요한 데이터를 먼저 선별한 뒤 하위 데이터 전체가 필요하다면 fetch join,  일부만 필요하다면 batch fetch를 이용하여 쿼리 실행 횟수를 줄일 것 같습니다. fetch join을 고려할땐 paging과 같이 쓰이는지 확인하고 메모리에 대한 사항도 고려해야합니다

### 개선안

SQL 로그와 실행 쿼리 수로 연관 데이터 조회가 반복되는지 확인하겠습니다. 필요한 연관 엔티티는 fetch join으로 함께 조회하고, 컬렉션을 포함한 페이징 조회는 부모를 먼저 페이징한 뒤 batch fetch나 별도 쿼리로 가져오겠습니다. 일부 필드만 필요하면 DTO 조회를 검토하겠습니다. 컬렉션 fetch join과 페이징을 함께 쓰면 메모리에서 페이징될 수 있으므로 생성 SQL과 경고 로그를 확인하겠습니다.

- 꼬리 질문: Redis 원자 선점과 DB `@Version`은 각각 어떤 책임을 갖나요?
- 꼬리 질문: Redis 선점을 꺼도 초과 판매가 0이었다면 선점을 둔 이유는 무엇인가요?
- 꼬리 질문: 낙관적 락, 비관적 락, 조건부 UPDATE, 유니크 제약 중 무엇을 선택하겠어요?

### 내 답변

<!-- 이 아래에 답변을 작성하세요. -->
먼저 redis의 원자성을 이용해서, redis에 잔여좌석의 각 id을 set에 등록한 후, srem에 대한 결과가 1인 요청만 좌석 예약을 진행합니다. 만약 redis의 fail over로 인해 2개 이상의 요청이 진행 되더라도, db에서 @Version을 이용한 낙관적 락을 통해 2중으로 동시 수정을 방지합니다

### 개선안

<!-- 이 아래에 답변을 작성하세요. -->
DB 갱신에 실패하거나 프로세스가 죽는다면 실제로 예약되지 않은 좌석이 사용자들에겐 이미 판매되었다고 표시됩니다. 하지만 이 상태는 최악 상황인 중복 판매는 아니고 일시적인 덜 파는 상태이기 때문에 감수합니다. 그리고 1분마다, DB와 redis의 차이를 확인한 후 redis에 미판매 좌석을 다시 추가합니다. 1분은 부하와 사용자의 오차확인에 대한 중간점이란 기준으로 정했습니다.

### 모범 답안
