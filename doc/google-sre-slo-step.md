Google SRE(Site Reliability Engineering)에서 **SLO(Service Level Objective, 서비스 수준 목표)** 설계는 무조건적인 높은 가용성을 추구하는 것이 아니라, ‘사용자가 만족할만한 최소한의 신뢰성’을 정의하고 개발 속도와 운영 안정성 사이의 균형을 잡는 작업입니다.

---

### 핵심 3요소 개념 구분

* **SLI (Service Level Indicator):** 서비스 수준 지표. 실제로 측정한 수치 (예: 성공 요청 비율, 응답 지연 시간).
* **SLO (Service Level Objective):** 서비스 수준 목표. SLI가 달성해야 할 목표 값과 기간 (예: 지난 30일간 요청의 99.9%가 200ms 이내 응답).
* **SLA (Service Level Agreement):** 서비스 수준 계약. SLO를 위반했을 때 발생하는 비즈니스/법적 보상 조건 (비즈니스 영역이며 SRE가 직접 설계하지 않음).

---

### Google SRE가 제안하는 SLO 설계 5단계 Step

1. **사용자 관점의 핵심 서비스 경로(Critical User Journey, CUJ) 파악**
* 내부 서버의 CPU 사용률 같은 시스템 지표 대신, **사용자가 체감하는 경험**에 집중합니다.
* *예:* "사용자가 상품을 검색하고 결제창까지 이동하는 과정"


2. **적절한 SLI 측정 항목 선정 (Four Golden Signals)**
* **Latency (지연 시간):** 요청 처리에 걸리는 시간.
* **Traffic (트래픽):** 시스템에 가해지는 수요 (초당 요청 수 등).
* **Errors (오류율):** 실패한 요청의 비율.
* **Saturation (포화도):** 시스템 자원 사용률 (CPU, Memory 등).


3. **측정 방식 결정 (측정 지점)**
* **클라이언트 측:** 사용자 실제 체감 수치 반영 가능하나 수집 난이도 높음.
* **로드 밸런서/API Gateway:** 구현이 가장 쉽고 범용적.
* **애플리케이션 로그/메트릭:** 상세 데이터 확보에 유리.


4. **현실적인 SLO 목표 수치 설정**
* 100% 가용성은 불가능하며 경제적으로도 비효율적입니다.
* **비즈니스 요구사항과 비용의 타협점**을 찾습니다. 99.9%에서 99.99%로 올리는 비용은 기하급수적으로 증가합니다.
* *예시 규정:*

$$\text{Availability SLI} = \frac{\text{성공한 요청 수}}{\text{전체 유효 요청 수}} \times 100$$


$$\text{SLO} = \text{지난 28일간 Availability SLI} \ge 99.9\%$$




5. **오류 예산(Error Budget) 연동**
* $\text{Error Budget} = 100\% - \text{SLO}$ (예: SLO 99.9% $\rightarrow$ Error Budget 0.1%)
* 오류 예산이 남아있다면 빠른 기능 배포(배포 위험 감수)를 진행하고, 예산이 소진되면 배포를 동결하고 시스템 안정화 작업에 몰두합니다.



---

### 설계 시 주의할 베스트 프랙티스

* **최소한의 지표만 유비:** 핵심 CUJ당 3~5개 이하의 SLO로 제한하여 복잡도를 낮춥니다.
* **퍼센타일(Percentile) 지표 사용:** 지연 시간을 측정할 때 '평균값'은 착시를 일으키므로 p50, p90, p99 퍼센타일을 활용합니다.
* **내부 SLO와 외부 공개 SLO의 분리:** 사용자에게 약속하는 외부 SLO보다 **내부 SLO를 더 엄격하게** 설정해 장애 발생 전 사전 대응 여유를 확보합니다.
